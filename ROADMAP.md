# Roadmap

## Core principle

`scan()` is lazy and streaming by default. Never materialize the whole dataset unless explicitly asked (`.collect()` / equivalent).

## Milestones

- [x] **M1 — Scanner**: file source, CSV parser, `next()`, row streaming, constant-memory, Zig API. Originally mmap-based; switched to fixed-size chunked reads (`src/root.zig`) after measuring peak RSS against `cat` on a 417MB/1M-row/51-col file — mmap held 426MB resident (touching every byte to scan it faults in, and keeps resident, every page: peak RSS == file size by construction, regardless of the scanner logic on top), `cat` held 1.4MB (fixed-size read-and-discard loop). Chunked reads bring `Scanner` down into that same regime — bounded by chunk size, not file size, so a 10GB file costs the same working set as a 10MB one. Almost every row is still a zero-copy slice into the current chunk; only a line that straddles a chunk boundary gets assembled into a small reused scratch buffer instead. `count()`'s no-WHERE fast path was adapted to count newlines chunk-by-chunk (`Scanner.countRemaining()`) rather than over one large mapped slice — same zero-field-parse property, still bounded memory. NDJSON and JSON arrays got the same treatment shortly after — see M4's updated entry below.

  Chunk size swept, not guessed: 10 runs each, same 417MB/1M-row/51-col file.

  | chunk size | time avg | RSS avg |
  |---|---|---|
  | 64KB | 0.577s | 2.01MB |
  | **256KB (default)** | 0.563s | 2.20MB |
  | 1MB | 0.562s | 2.96MB |
  | 4MB | 0.565s | 6.13MB |
  | 16MB | 0.600s | 18.73MB |

  Time is flat (0.56-0.58s) from 64KB through 4MB — syscall count isn't the bottleneck anywhere in that range, even at 64KB (~6,500 `read()` calls for this file). RSS scales roughly linearly with chunk size, with no time payoff for going bigger. 16MB is a strict loss on both axes — the buffer itself gets big enough that first-touch cost starts to show. Landed on 256KB as the default: same time as 1MB, 26% less RSS, with enough margin over 64KB to avoid its slightly wider run-to-run variance. At the chosen default, versus the old mmap version: 427MB -> 2.2MB peak RSS, ~30% slower (0.43s -> 0.56s single-thread) — a real, named tradeoff made for the memory win, not hidden.

  Chunk size is configurable, not hardcoded: `Scanner.openWithOptions(allocator, path, .{ .chunk_size = N })` directly, or `Query.open(allocator, path, .{ .csv_chunk_size = N })` — `null` (the default either way) uses the measured 256KB default. Not exposed through the C ABI or Python binding yet (both use the default); add if a real caller needs to tune it, not speculatively.
- [x] **M2 — Scan operations**: projection, filter, limit, first, count. `count()` with no WHERE clause takes a zero-field-parse fast path (raw newline counting on the mapped bytes) — measured ~10x faster than a full row scan on a 500K-row file. `limit(N)` returns in time proportional to N, not file size (measured near-instant regardless of file size).
- [x] **M3 — C ABI**: `scanio_open` / `scanio_next` / `scanio_count` / `scanio_column_index` / `scanio_close` / `scanio_last_error`, minimal, no Zig internals exposed. Allocator is `std.heap.c_allocator`, not `GeneralPurposeAllocator` — this library gets `dlopen()`'d into a host process, and GPA's PageAllocator faults there (the exact bug csvql shipped once, #149). Verified for real: `zig build smoke-test` loads the built `.dylib`/`.so` via Python `ctypes` — the actual `dlopen()` path, not just Zig's in-process test runner — and runs 200 consecutive open/close cycles to catch allocator faults that only surface after repeated use.
- [x] **M4 — NDJSON, plus JSON arrays**: `src/ndjson.zig`, wired into `Query` via a `Source` tagged union so `scan("data.csv")` and `scan("data.ndjson")` (format inferred from extension, or explicit override) behave identically at every layer — filter, projection, limit, and the newline-only `count()` fast path all work the same for both, since both formats are one-record-per-line. `.json` files are also routed to the NDJSON path; the first non-whitespace byte (sniffed from the first chunk, see below) decides NDJSON-lines vs JSON-array. Nested objects/arrays *as field values* are still out of scope and fail loudly (`NestedValueNotSupported`) rather than silently stringifying.

  Originally mmap/full-load, same as CSV was before M1's fix, and for the same reason: measured 57.7MB peak RSS on a 56MB/1M-row NDJSON file and 51.1MB on an 11MB/200K-row JSON array file — both tracking file size, not row count. Rebuilt on the same chunked-read foundation as CSV (`NdjsonScanner` now has its own `buf`/`buf_len`/`buf_pos`/`line_scratch`, same shape as `Scanner`'s). NDJSON lines use the identical newline-boundary `nextLine()` CSV already has. JSON arrays needed a different boundary rule — no newlines to rely on inside `[{...},{...}]` — so `nextObject()` tracks brace depth and in-string/escape state across chunk refills instead, extracting one balanced `{...}` at a time; the old `json_array.zig::jsonArrayToNdjson()` (convert-the-whole-array-up-front) is no longer called by this path, kept only as a tested reference implementation. The header is derived from the first row's keys at `open()` time (same schema model as before) and that first row's text is cached and replayed as the first `next()` result, since a chunked reader can't rewind a file position the way a full mmap could.

  Measured, 10 runs each, old (mmap/full-load) vs new (chunked/streaming):

  | | time avg | RSS avg |
  |---|---|---|
  | NDJSON old, 56MB/1M rows | 0.176s | 57.72MB |
  | **NDJSON new** | 0.174s | **1.98MB** (29x less) |
  | JSON array old, 11MB/200K rows | 0.033s | 51.10MB |
  | **JSON array new** | 0.050s | **1.97MB** (26x less) |

  NDJSON's win is essentially free — same speed, 29x less memory, since line-splitting was never the bottleneck (JSON parsing dominates either way, unaffected by the I/O layer change — verified in isolation before trusting the headline number, since an earlier run of this same comparison showed a bogus 18x *slowdown* that turned out to be a stale, un-rebuilt benchmark binary, not a real regression). JSON array's win costs ~50% more time — the streaming brace-depth scan does genuinely more structural work per byte than one bulk convert pass followed by ordinary line-splitting did. Both are now bounded by chunk size regardless of file size, matching CSV and `cat`.

  Later, real correction: every NDJSON/JSON-array throughput number above (4.3-6.0M rows/sec) used a 3-4-field test fixture. Measured against a real 51-column NDJSON file (the same taxi CSV data used everywhere in this project, converted to NDJSON) and got 187K rows/sec — 23x slower for 17x more fields, the signature of O(n^2) cost. Root cause: `next()` looped over every header key and called `JsonObject.get()` (a linear scan over the row's own fields) once per key. Fixed with `header_index` (`src/ndjson.zig`) — a hash map from header key to column index built once at `open()` — turning the lookup into one pass over each row's own fields instead of one pass per header key. Isolated before AND after fixing it: parse-only (no lookup at all) measured 242K rows/sec on the same wide fixture, meaning the fixed lookup now costs ~13% overhead (210K vs 242K rows/sec) instead of being the dominant cost. Narrow fixtures unaffected (4.1-4.3M rows/sec, unchanged). The remaining 242K rows/sec ceiling on wide rows is JSON parsing itself (tokenizing, escaping, building `Field` structs — costs that scale with field count regardless of lookup strategy), a different, harder lever than this one was.

  Pushed on that lever, not just accepted it: isolated SIMD tokenizing alone (`findJsonStructure`, no field extraction) at 778K rows/sec on the same wide fixture — 3.2x above the 242K parse-only number, confirming (as the old tok_bench claim said) that tokenizing is NOT the bottleneck; per-field key/value extraction is. Read every function in that extraction path (`parseObjectReuse`, `parseValueAfterColon`, `findStringEndFromTokens`, `advanceTokenIndex`, `hasJsonEscape`) looking for another O(n^2)-class bug like the header one — found none: both key and value extraction are O(1) per field (monotonic token-index advance, zero-copy string slices for the unescaped case this fixture hits). Added a positional fast path anyway (`src/ndjson.zig` `next()`) — real NDJSON files usually keep stable key order row-to-row, so checking `obj.fields[k].key == header[k]` by `mem.eql` first, before falling back to `header_index.get()`, skips hashing entirely on the common case. Measured its effect honestly: 204K-234K rows/sec across repeated runs, overlapping the pre-change 210K within noise — kept the change (correct, harmless, directionally right for stable-order files) but did NOT report it as a proven win. That "not a remaining algorithmic bug" conclusion was wrong — it was scoped to the extraction loop, not the SIMD tokenizer itself, and the tokenizer had a real, fixable inefficiency: `findJsonStructureN` (`src/json_simd.zig`) found structural chars with a per-lane `if (!is_any[j]) continue` scalar loop over every lane of the SIMD chunk (16 bytes at a time), even though real JSON text is sparse in structural chars — most of a 51-field row is string/number content between them. That loop's branch is data-dependent on where structural chars fall, so it mispredicts constantly on real content, not the tidy `{"a":1,"b":2}` pattern short benchmarks tend to use. Fixed with the standard simdjson technique: convert the SIMD match vector into a bitmask (branchless — shift-and-or per lane, no data-dependent conditional) and walk it with `@ctz` + clear-lowest-set-bit, which visits exactly `popcount(mask)` positions instead of scanning all 16 lanes every chunk. Measured on the same wide (51-field) fixture, repeated 3x for stability (209K-234K noisy before vs 313K-315K tight after): full `next()` went from ~210-230K rows/sec to a consistent ~313-315K rows/sec — a real ~40-50% gain, not noise (variance itself dropped, a second signal it's a genuine fix, not a lucky run). JSON array format (shares the same tokenizer) went 132K → 167K rows/sec, ~26% up. Narrow (3-field) fixture unaffected/slightly up (4.99M rows/sec, matching the old 4.1-4.3M baseline) — confirms the fix helps proportionally more where structural-char density is lower (wide rows, long string values), exactly where the old per-lane scan cost the most. Full Zig/Python/Node test suites re-verified green after the change.

  Still not CSV speed (CSV: ~2.1-2.2M rows/sec on the same wide fixture; NDJSON at 313-315K was ~7x slower), and told so directly. The real remaining cost wasn't another bug in the generic pipeline — it was the generic pipeline itself: building a Token array, a Field-struct array, and tagged JsonValue unions for data this scanner only ever reads back as raw strings is pure overhead CSV's comma-split never pays. Added `NdjsonScanner.tryFastRow()` (`src/ndjson.zig`) — a fused, single-pass byte scanner straight into `field_buf`, the same shape as CSV's own line-splitting, used only when a row matches the fast shape (same key order as the header, no escapes, no nested values); falls back to the full generic parser — unchanged, still the correctness source of truth — the instant anything doesn't match, so correctness never depends on the fast path succeeding. First version (using json_parser's manual per-byte escape-tracking `findStringEnd`) reached ~440-460K rows/sec. Checked `zson` (this parser's own ancestor project, `~/code/birim.one.dev/zson`) for a faster single-row technique — found none; `zson`'s `json_parser.zig` is a strict subset of this one (no `parseObjectReuse` equivalent), and its actual speed lever is `parallel_ndjson.zig`, multi-threaded chunked processing, not a smarter single-row parse. Applied the one real single-row win available: replaced the manual escape-tracking string-end scan with vectorized quote search (`std.mem.indexOfScalarPos`, SIMD-backed) plus a cheap backward escape-check only on an actual hit (`findQuoteEnd` in `src/ndjson.zig`) — the string equivalent of CSV's own comma search. That took the fast path to a stable ~510-540K rows/sec (3x runs, tight variance) — ~65% up from the pre-fast-path 313K, ~2.5x up from where this investigation started (210K). Narrow (3-field) fixture, JSON array format, and all Zig/Python/Node (46/46) test suites re-verified after this change too.

  Honest ceiling assessment: closing the remaining ~4x gap to CSV's 2.1M would mean either (a) genuinely inherent JSON cost CSV doesn't have — pairing two quotes per field (key + value) versus CSV's one delimiter search, even at SIMD speed, is real extra work per field — or (b) matching zson's actual lever, multi-threaded chunked parsing, which is a materially bigger architectural change: it breaks the single-threaded, bounded-memory `next()`-generator contract every consumer (C ABI, Python, Node, MCP) currently relies on, and hasn't been attempted here. Not pursued without explicit direction, since it changes the API contract, not just the algorithm.

  External checkpoint, not just self-comparison: benchmarked two other JSON parsers on the identical wide fixture, same job (extract all 51 fields/row), to check whether "still not CSV speed" meant libscanio specifically was slow or JSON itself is: Zig stdlib's own `std.json.Scanner` (the lowest-level streaming API it ships, no tree-building) measured ~273-280K rows/sec — libscanio's fast path (~510-540K) is already ~2x that. Real simdjson (the actual C++ reference implementation, installed via `brew install simdjson`, used through its On-Demand API — same lazy per-field-extraction shape as libscanio's fast path, not full-DOM parsing) measured ~710-745K rows/sec, single-threaded, via a small harness compiled against `libsimdjson`. Even the industry-reference SIMD JSON parser doesn't get near CSV's 2.1-2.2M on this data — confirms the ~4x CSV gap is structural to JSON (two quote-pairs per field vs one delimiter), not a libscanio shortfall. libscanio sits within ~1.4x of simdjson itself.

  Tried to close more of that 1.4x gap: attempted simdjson's actual technique — fuse the quote-search and escape-detection into one scan (find next `"` or `\`, whichever comes first) instead of two separate passes (`findQuoteEnd` then a full re-scan via `hasJsonEscape`). Implemented as a hand-rolled fixed-16-byte-chunk SIMD scan (same bitmask+`@ctz` shape as the earlier `json_simd.zig` fix). Measured it: a real regression, ~431-462K, worse than the ~510-540K baseline it was meant to improve. Root cause, confirmed by reading `std.mem.indexOfScalarPos`'s actual implementation: Zig stdlib already uses a tiered SIMD strategy (full vector blocks sized via `std.simd.suggestVectorLength`, then half, then quarter, then a scalar tail) that's well-tuned for short slices — most field values in this fixture are under 16 bytes, so the hand-rolled version's fixed-chunk threshold pushed those straight to a slower two-condition (quote-or-backslash) scalar loop instead of getting any vectorization at all. Reverted (`git checkout -- src/ndjson.zig`), confirmed back to the known-good, faster, committed version. Lesson worth keeping: a hand-rolled fixed-chunk SIMD routine isn't automatically better than calling stdlib's primitive twice — check what the primitive actually does before assuming a "fused" rewrite wins.

  Where this landed, not chased further without explicit direction: closing the remaining gap to simdjson's actual number means porting its real two-stage architecture (one pass over the *entire* document computing structural-character and string-boundary bitmasks together via carry-less multiplication, then a lazy second pass over a compact structural index) — a genuine rewrite, not a per-field tweak. Current state: NDJSON wide-fixture throughput went 187K (session start) → 210K (O(n^2) header-lookup fix) → 313K (SIMD tokenizer bitmask fix) → 510-540K (fused fast-path row scanner + vectorized quote search), a ~2.9x total improvement, verified 2x faster than Zig's own stdlib JSON scanner and within ~1.4x of the C++ reference implementation. Full Zig/Python/Node (46/46) test suites green throughout.

  | file (real taxi data, same 1M rows) | format | size | rows/sec | peak RSS |
  |---|---|---|---|---|
  | sample.csv | CSV | 417MB | ~2.1-2.2M | ~2.2MB |
  | sample.ndjson (51 fields) | NDJSON | 1.47GB | ~205K | ~2.0-2.1MB |
  | sample_array.json (51 fields) | JSON array | 1.47GB | ~132K | ~2.0-2.1MB |
  | sample_narrow.ndjson (3 fields) | NDJSON | 70MB | ~4.1-4.3M | ~2.0MB |

  Memory stays flat across every format and field count — the chunked-read design applies uniformly, not just to CSV. Speed does not: JSON's per-row parsing cost (SIMD tokenizing, escaping, object construction) that CSV's flat field-split never pays, plus JSON's own verbosity (repeating every key on every row — the 51-field NDJSON file is 3.5x the CSV file's size for the same data) explain most of the CSV-vs-JSON gap; JSON array trails NDJSON further (~1.5x slower) from the streaming brace-depth scan's real structural cost.

  Three real findings from actually measuring this, not assuming:

  1. The first implementation used `std.json.parseFromSlice` per line and measured 42K rows/sec vs CSV's 17M — 400x slower, building a full parse tree per row is real cost. Fixed by pulling in `json_parser.zig`/`json_simd.zig` from [zson](https://github.com/melihbirim/zson) (MIT, same author, vendored into `src/`) — a SIMD-tokenized, zero-copy JSON line parser already solving exactly this problem.
  2. Swapping the parser alone did *not* fix it — throughput was still ~39K rows/sec. The actual bottleneck was `std.heap.GeneralPurposeAllocator`'s per-allocation tracking overhead, not the parsing algorithm; switching the allocator passed to `Query.open()` to `std.heap.c_allocator` took it to 2.78M rows/sec — a 66x difference from allocator choice alone, on the identical parser and file. The C ABI already used `c_allocator` for an unrelated reason (GPA also faults when `dlopen()`'d), so Python callers got the fast path automatically the whole time — only the raw Zig-API benchmarks were measuring the slow path.
  3. Even with `c_allocator`, `NdjsonScanner` was still allocating and freeing a fields array (plus any escaped strings) fresh every row — a malloc/free pair per row, where CSV's `Scanner` does zero allocations per row via a reused, grow-not-reallocate `field_buf`. Replaced that with a `std.heap.ArenaAllocator` reset (`.retain_capacity`) at the start of each `next()` instead of individually freeing the previous row's `JsonObject` — reuses the same block across rows rather than returning it and re-requesting it every time, and skips `JsonObject.deinit()`'s per-field cleanup traversal entirely (arena reclaims everything in one reset). Took it to **4.3M rows/sec**.

  Final numbers, 500K rows: CSV 19.7M rows/sec / 12.8MB peak RSS, NDJSON 4.3M rows/sec / 25.4MB peak RSS — about 4.5x slower and 2x more memory than CSV. Not zero-copy parity (JSON structurally needs a per-row data structure CSV's flat field-split never does), but no longer 400x off, no longer unbounded, and now within the same order of magnitude as CSV rather than two orders away. Peak memory unchanged by the arena change — it retains the high-water-mark block rather than shrinking, a deliberate speed-over-footprint tradeoff, still bounded rather than growing.

  4. Done next: added `parseObjectReuse()` to `json_parser.zig` — same parsing logic as `parseObject()`, but the caller supplies a `fields` array to `clearRetainingCapacity()` and refill instead of a fresh `std.ArrayList` + `toOwnedSlice()` per call, same discipline CSV's `field_buf` already uses. `NdjsonScanner` holds that array as a persisted field, grown once via a real allocator and reused for the scanner's whole lifetime — not the per-row arena, which would defeat the reuse. One real bug this surfaced, caught by this file's own test suite (`ndjson: escaped strings decode correctly`): `owned_strings` (tracking escaped-string allocations) can't be persisted the same way, because `parseValueAfterColon()` grows *that* list using whatever single allocator it's handed — which for the reuse path is the per-row arena — so its backing array is arena-scoped, and freeing it later via the scanner's real allocator (a different allocator than whatever actually backed it) segfaulted. Fixed by keeping `owned_strings` local to each `next()` call instead of a persisted field.

  Effect depends on call pattern, reported honestly rather than picking whichever number looks best: in a **cold, single-process run** (the shape of a one-shot CLI/script invocation — `mem_check` scans once and exits), throughput went from 4.3M to 4.7M rows/sec — a modest ~10%, since first-touch costs (page faults, cold caches) dominate a short-lived process regardless of whether the code reuses buffers. In a **warm, repeated-call pattern within the same process** (5 runs back to back, first discarded), it went from an unmeasured baseline to a **steady ~6.0M rows/sec** — the reuse benefit compounds across calls once the working set is warm. CSV's own steady-state also jumps with warm-cache repetition (cold ~20M, warm ~44M on this hardware), so the CSV-to-NDJSON ratio lands around 4-7x depending on which regime you're comparing, not a single fixed number.

  Remaining lever, not yet done: the fields array is reused, but each row's *values* still get individually decoded/copied when escaped; a fully zero-copy path (only ever copying bytes that genuinely need unescaping, never touching the allocator for unescaped strings/numbers at all — which the parser mostly already does, per-field, but the per-row bookkeeping around it still costs something) is the next place to look if this needs to go further.
- [x] **M5a — Python binding**: `libscanio.scan(path, columns=[...], where="...", limit=...)` — the original target API. WHERE is a simple string (`col OP val [AND col OP val ...]`, no OR — the C ABI only represents a flat AND-list, and nothing has needed more than that yet). Column names are resolved to indices via one throwaway `scanio_open()` before the real, options-bearing open (the C ABI has no header-only entry point; two mmaps of the same file, not two reads, so the OS page cache absorbs it). Building this binding is also what surfaced a real C ABI gap — no way to list header column names — closed by adding `scanio_n_columns`/`scanio_column_name` to M3's surface rather than working around it in Python. Verified via `zig build python-test`, the real dlopen() path via ctypes, not just Zig's in-process tests; caught one real bug this way (two new C ABI functions missing from the ctypes `argtypes`/`restype` declarations caused a segfault — ctypes defaults to a 32-bit `c_int` return type, which mangles a 64-bit pointer/size_t).

  Later addition — `col IN (a, b, c)`: still no general OR (the C ABI's predicate list is still flat-AND-only), but IN covers the one case that gap actually blocked — "any of these values" — without needing N separate scans unioned in Python. New `Op.in_list` in `query.zig` (a predicate carries `values: []const []const u8` instead of one `value` when this op is used), a new `SCANIO_IN` C ABI op plus `values`/`n_values` fields on `scanio_predicate_t`, and `col IN (...)` syntax in the Python WHERE-string parser. One real ctypes gotcha worth naming: the `values` pointer in a `CPredicate` points at a ctypes array (`c_char_p * N`) that Python doesn't automatically keep alive just because a `CPredicate` references it — `_parse_where()` now returns that array alongside the predicates list (as `keepalive`) and every caller holds it in scope through the `scanio_open()` call that actually reads it, otherwise it risks being garbage-collected before or during the C call. Verified end to end on the real 417MB taxi fixture: `cab_type IN (yellow, green)` returned exactly 1,000,000 — matching the file's total row count, confirmed correct (not a bug) by checking yellow (967,553) + green (32,447) sums to exactly that.
- [x] **M5b — Node binding**: `node/` — same shape as the Python binding (`scan`/`scanArray`/`schema`/`count`/`aggregate`/`topk`/`profile`), originally via [koffi](https://koffi.dev) (dynamic FFI, no native compilation step, same "works right after install" property `ctypes` gives the Python side). Node has no built-in FFI (unlike Bun's `bun:ffi`); the alternative considered at the time was a native N-API addon — zero runtime npm dependency, but needs a native build per platform, real setup cost not taken on for a first Node binding. **Superseded: koffi had a real, unfixable-from-this-side Windows crash (see the Honest gaps entry below) and was replaced entirely with a real N-API addon** — the "real setup cost" concern here turned out smaller than the cost of koffi's Windows bug once it actually mattered.

  Real question raised before building it: would an FFI-via-npm-package layer cost meaningfully more than Python's `ctypes` did? Measured directly, same rigor as the ctypes investigation — pure Zig (`examples/collect_bench.zig`, no JS at all) vs `scanArray()` through koffi, same file, same query: low-selectivity (26 matches) added ~30-40ms fixed overhead (0.12-0.14s -> 0.157-0.172s); high-selectivity (967,553 matches) scaled to 0.341s -> 0.656-0.849s, but that increase tracks almost exactly what Python's `ctypes` path showed for the identical query (0.687s) — meaning it's the cost of constructing ~2M JS objects, not a koffi-specific FFI tax. koffi isn't a special problem; object-materialization cost is a property of the host language, not the binding technology.

  Design carried over exactly from the Python binding, including the parts that mattered: `stop_after_column`/`max_column` bounding computed the same way (safe for `scan()`/`scanArray()` only when `columns` is explicit, always safe for `count()`/`aggregate()`, deliberately NOT applied to `topk()` since it returns full rows and bounding would silently truncate them); the same WHERE-string grammar (`col OP val [AND ...]`, `col IN (a, b, c)`); the same bulk-collect path (`scanArray()`, one `koffi.decode()` bulk buffer read instead of one FFI call per field per row) for when a caller wants the whole result materialized fast rather than streamed. One real memory-safety question this raised, given the Python binding's use-after-free (predicates freed while `scan()` still read them): tested directly whether koffi has the same problem — forced GC pressure with 500 throwaway `Buffer.alloc()`s between every `scanio_next()` call on a WHERE-filtered scan, verified the result stayed correct across 300 calls. koffi manages string-argument memory safely across calls (unlike whatever ctypes' array-copy path was doing); kept as a permanent regression test in `node/test/test.js` anyway, same reasoning as the Python side — verified once isn't the same guarantee as verified forever.

  Verified via `zig build node-test` (36 tests, real `dlopen()` through koffi, not a mock) and directly against the real 417MB taxi CSV (967,553-row filtered result, byte-for-byte correct) — on macOS and Linux. **Windows is a known gap, not silently missing**: `scanio_open()` crashes outright through koffi on Windows CI (zero output, exit code 5 — no JS stack trace, meaning it's a native crash inside koffi's FFI engine, not a normal JS exception) regardless of what's passed for the options argument. Traced to that exact call via added FFI-call logging (`LIBSCANIO_DEBUG=1`, `node/lib/loader.js`), then tried two different targeted fixes — a struct-layout-mismatch theory and a null-struct-pointer theory (`NO_OPTIONS` in `node/lib/index.js`) — neither changed the outcome.

  **Revisited directly, not left as a stale gap.** Checked koffi's own changelog for real Windows-specific fixes since this was diagnosed — found genuine Win64 stability work in 3.1.4 (clearing unused register/stack bytes when pushing bool arguments) and 3.1.5 (reverted to native compilation for Windows build stability), both predating the pinned 3.2.0. Upgraded to 3.2.1 (latest at the time) and retested on real Windows CI — same crash, same exit code 5, same call site. That theory is now ruled out too.

  Built a precise diagnostic (`node/test/windows_diag.js`, kept as a permanent repro artifact, not deleted after use) to narrow it further: a zero-arg, `str`-returning call (`scanio_last_error()`) works fine on this Windows runner — koffi itself isn't broken. `scanio_open(path, null)` — a bare 2-arg call, second argument a raw NULL pointer, no struct involved at all — crashes at the exact same point. **This rules out struct marshaling entirely**, which the original struct-layout theory assumed was the cause; the crash doesn't need a struct to happen. And it isn't libscanio's own code either: `examples/smoke_test.py` calls `scanio_open(path, None)` via Python's ctypes — the IDENTICAL call shape — and it passes cleanly on the same Windows runner, same CI run. The bug is now precisely isolated to **koffi's own Windows FFI dispatch for this specific call shape (2 arguments, one a pointer, `void*` return)** — not libscanio's Zig code, not struct handling, not this specific koffi version. Real next step, not yet done: file this as a minimal, reproducible upstream koffi issue (`windows_diag.js` already IS that minimal repro) rather than keep guessing blind from this side — the fix, if there is one, is inside koffi's own Windows trampoline generation, out of this project's reach to patch directly.

  Follow-up, once real workload comparisons surfaced it: `libscanio.scan(...)` materialized into a Python list (`list(scan(...))`) was measured *slower* than a naive `csv.DictReader` loop doing the same filter in pure Python — 22.5s vs 10.8s on the 417MB/1M-row fixture, unprojected. Root cause: `scanio_next()` is one FFI call per row, and each row needs one `.decode()` per field — ~2M individual Python/C boundary crossings for a ~967K-row result, and that per-call cost dominates once you want every matching row back as real Python objects, not just a count.   `scan_array()` is deliberately NOT memory-bounded the way `scan()` is — it materializes every matching row in both Zig and Python at once, same tradeoff any "give me an array" API has. - [x] **Bounded field-splitting (`stop_after_column`)**: `splitInto()` used to split every field of every row regardless of what the query actually reads — real cost, discovered by fairly comparing libscanio against xan (a real Rust CSV tool, same weight class) and finding libscanio lost by ~1.35-1.5x on low-selectivity queries despite winning on high-selectivity ones. Root cause, confirmed with a pure-Zig benchmark (`examples/collect_bench.zig`, no Python layer at all, to rule out ctypes overhead first) before touching anything: at low selectivity almost every row gets scanned and discarded, so the per-row scan cost dominates — and libscanio was scanning 51 fields to answer a question that only needed 2-6 of them.

  Fix: `ScannerOptions.stop_after_column` (new, `src/root.zig`) — `splitInto()` stops the instant it's captured the highest column index the caller will ever read, never scanning the rest of the line's bytes at all, not just discarding them. Threaded through `QueryOptions.stop_after_column` (`src/query.zig`), the C ABI's new `COptions.max_column` (`-1` = unbounded/old behavior, the safe default), and computed automatically in the Python binding: `scan()`/`scan_array()` bound it to `max(projected columns, WHERE columns)` whenever an explicit `columns` list is given (columns=None still means "need everything," correctly left unbounded); `count()`/`aggregate()` bound it to WHERE columns plus (for `aggregate()`) the analysis column, since neither ever returns row data so it's always safe. `topk()` deliberately was NOT given this treatment — it returns full-row dicts (every column, not just the sort column) as documented behavior, and bounding it would silently truncate that; revisit only alongside a real API contract change, not as a silent optimization.

  Real ctypes gotcha this surfaced: `COptions` gained a new field (`max_column`) but ctypes zero-initializes any Structure field not explicitly passed to the constructor — every single `COptions(...)` call site in the Python binding had to be updated to pass it explicitly, or it would have silently defaulted to `0` (meaning "only column 0 is ever needed"), a correctness bug far worse than no optimization at all. Caught before it shipped by grepping every construction site, not by a test that happened to notice.

  Measured, same 417MB/1M-row taxi file, `rate_code_id = 6` (26 matches, column 5 of 51 — an early/low-selectivity case): pure Zig 0.44s -> 0.13s (3.6x), and through Python `scan_array()` 0.45s -> 0.15s (3x) — beating xan (0.30s) by ~2x, reversing the earlier loss outright. Mid-row case (`payment_type = DIS`, column 20, 1,085 matches): 0.45s -> 0.27-0.29s, now roughly tied with xan (0.29-0.30s) instead of 1.5x behind.   Design decisions made explicitly before writing code (asked, not assumed, since both are real API-shape choices): (1) keep the bounded-memory guarantee M1 exists for — ruled out csvql's own `src/parallel_mmap.zig` approach (a real, working reference: mmaps the whole file, splits into N line-boundary-aligned byte ranges, one `std.Thread` per range) specifically because mmap-ing the whole file re-introduces the exact peak-RSS-equals-file-size problem M1 moved away from. (2) keep `Query.next()`'s single-threaded streaming contract completely untouched — parallel scan is a separate, explicitly-opted-into entry point, not a change to the generator every consumer (C ABI, Python, Node, MCP) already depends on; threading a per-row streaming API means either buffering full results up front (defeats streaming) or a cross-thread ordered merge queue (thread pool lifecycle now has to survive across `next()` calls, dlopen()-safety needs re-verifying for every binding) — out of scope for a first slice.

  `src/parallel.zig`: each worker thread does its own `WORKER_CHUNK_SIZE`-bounded `pread()` loop over a disjoint byte range of ONE shared `std.fs.File` handle — `pread()` (POSIX `pread(2)`; Windows `ReadFile` with an explicit `OVERLAPPED` offset) doesn't touch a shared file-position cursor the way `read()` does, so concurrent `pread()` on one handle is safe without needing a file open per thread. Peak RSS bounded by `WORKER_CHUNK_SIZE * num_threads`, not file size. Range boundaries aligned to the next newline via a small growing-window `pread()` (starts at 64KB, doubles only if a single line is pathologically longer — never reads the whole remaining file just to find one boundary).

- [x] **M12 — validate() (import validation)**: `src/validate.zig` — check every row against a schema in one streaming pass and report which cells broke which rule. Motivated by a plain observation: CSV files mostly arrive to be *loaded*, and a loader's question is the inverse of `scan(where=...)` — not "which rows do I want" but "which rows can I not take, and why", with a reason per cell that can be shown to a human.

  Shape decided before writing code, and one obvious option deliberately rejected: **not** two materialized arrays of valid/invalid rows. That would make peak memory scale with the file, in the one feature whose whole justification is running over an import too big to load. Instead `Validator` streams `(row, errors)` and `validate()` is a bounded summary built on it — every error counted, only the first `max_errors` (default 100) stored, `truncated` saying so. A wholly-broken 40GB file therefore produces a report, not an OOM; that is precisely the file you most want a report about. The streaming form is what an actual import uses: good rows to the target, bad rows to a rejects file, in the same pass, neither side materialized.

  Rules: `type` (`any`/`integer`/`float`/`boolean`/`datetime`/`string`), `required`, `min`/`max`, `min_len`/`max_len`, `one_of`. Chosen to be the set that needs no new machinery — no regex engine (Zig has none in std, and vendoring one is a subproject, not a rule), no state proportional to the file. **Uniqueness and referential checks are excluded on purpose**: both need a set of every value seen, which is the one thing this library promises not to build; they belong in the database doing the import, which already has the index.

  Semantics chosen deliberately, each because the alternative produces an unreadable report: a blank cell is *absent*, not badly typed (only `required` speaks to it, so a sparse optional column doesn't emit one `bad_type` per row); `required` treats whitespace-only as blank, which is what a spreadsheet leaves behind when a cell is cleared; lengths count characters, not bytes (`max_len: 6` passes `Zürich`); structural errors (`too_few_fields`/`too_many_fields`) are reported once per row rather than as one `missing_required` per absent column; a wrong-typed cell reports `bad_type` and stops, since its range and length are not news. Reusing `query.zig`'s `parseNumeric` for `float` keeps `"nan"`/`"inf"` classified as text here exactly as they already are in every predicate, aggregate and sort in the library.

  **Evaluated in Zig, not composed per binding** — the opposite of the `profile()`/`describe()` precedent, and for a stated reason: those are sampled heuristics where a small divergence is a nicety; this decides whether a row loads. Three clients re-implementing "is this an integer" is three subtly different answers, and an import that passes in Python and fails in Node is worse than no validation. The schema crosses as JSON and is parsed once, in Zig. An unknown column name or a misspelled rule name is an error rather than a silently unenforced rule, on the same reasoning.

  Surface: C ABI (`scanio_validate`/`scanio_validate_json`/`scanio_validate_free` for the report; `scanio_validator_open`/`_next`/`_close` plus running totals for the stream — errors arrive as a JSON array per row, and NULL for a clean row, so the common case allocates nothing on either side), Python (`validate`/`validate_iter`/`infer_schema`), Node (`validate`/`validateIter`/`inferSchema`), CLI (`--validate <schema.json>`, `--valid`, `--invalid`), MCP (`validate`, `infer_schema`). Report mode exits 1 when any row failed, so it drops into a shell script as a gate; the two row modes exit 0 whenever they ran, so a pipeline under `set -e` is not aborted by the very rejects it asked to see. `--validate` refuses to combine with `--where`/`--columns`/`--limit`/`--count` rather than silently ignoring them.

  Node's handle registry was generalized (`HandleRegistry(T)`) rather than copied for the validator — the same ID-not-pointer lookup and the same `in_use`/`close_requested` reentrancy rules now serve both, so the use-after-free fix that registry exists for cannot be half-applied to one of them.

  Verified four ways: 16 Zig unit tests (rules, blank handling, structural errors, the `max_errors` cap, UTF-8 lengths, NDJSON parity, quoted CSV, bad schemas), 4 C ABI tests including null-argument handling, 25 Python and 20 Node binding tests through the real dlopen()/N-API paths, and — the one that matters for the "one implementation" claim — 79 new `zig build diff-test` checks running seven schemas across an eight-row adversarial fixture through an **independent Python oracle written from the documented semantics**, then Python vs Node vs CLI, including the streaming form against the report, the CLI's exit code, and `--valid`/`--invalid` partitioning the file exactly as the report says. That oracle was perturbed on purpose to confirm it fails when the implementations disagree (25 failures), not merely that it passes.

  Measured on a 126MB/3M-row/10-column CSV, four rules over four columns:

  | | median | throughput | peak RSS |
  |---|---|---|---|
  | `scanio --count` (no field split, for scale) | 0.02s | 5,120 MB/s | 10.1MB |
  | `scanio` full scan, every field split | 0.27s | 460 MB/s | 10.0MB |
  | **`scanio --validate` (report)** | **0.49s** | **257 MB/s** | **10.1MB** |
  | `libscanio.validate()` (Python) | 0.48s | 263 MB/s | 10.9MB |
  | `libscanio.validate()` (Node) | 0.50s | 253 MB/s | 46.1MB (V8 floor) |
  | hand-written Python `csv` loop, same four rules | 4.37s | 29 MB/s | 10.1MB |

  The four rules cost about as much again as the parse they run on (0.27s → 0.49s), and memory is indistinguishable from a plain scan — the bounded-report design doing what it was designed for. 8.9x faster than the hand-written Python loop while doing strictly more (structural checks, character-not-byte lengths, RFC 4180 quoting). The per-row streaming forms cost 11.4s (Python) and 7.8s (Node), against 9.0s for `scan()` alone over the same file: there the per-row crossing into the host language dominates and validation is the smaller half of it. Both numbers are reported rather than only the flattering one — the report form is what to reach for when the summary is what you want.

**M9 follow-up — real JSON-array parallel WHERE filtering, closing the gap M9's own entry left open.** `parallelCountRowsWhere()` previously delegated JSON arrays to the single-threaded `Query` path, reasoned as a deliberate non-duplication since a bare count's boundary walk already costs what the count does. Direct request to close that gap anyway, on the theory that WHERE-filtered work (real per-object JSON parsing + predicate matching, the expensive part) genuinely benefits from parallelism even though a bare count doesn't. Implemented: `findJsonArrayRanges()` — one sequential pass (same brace-depth/in-string/escape state machine as `countJsonArrayObjects()`, refactored into a shared `walkJsonArrayObjectCloses()` so both use one copy of the logic) records up to `num_threads` object-boundary-aligned byte ranges; `forEachJsonObjectInRange()` walks complete objects within one range (same chunk-boundary-carry shape as `forEachLineInRange()`, tracking a balanced `{...}` instead of a `\n`); `buildJsonArrayHeader()` derives the header from the first top-level object instead of a first line; `JsonArrayFilterWorker`/`JsonArrayFilterCtx` parse+match per object per thread, same shape as the NDJSON filter worker.

Verified correct across explicit thread counts (1, 2, 3, 7, 16 — including odd splits that don't evenly divide the object count) on the real 1M-object wide fixture (`/tmp/sample_array.json`, 1.47GB), every count matching `Query.count()` exactly.

Two real, logged, reverted attempts at speeding up the sequential boundary walk itself — worth keeping the record, not just the final working version: (1) A fixed-16-byte-chunk bitmask+`@ctz` scan (the exact technique that fixed `json_simd.zig`'s tokenizer earlier this session) was tried first and REGRESSED (3.06s → 4.10s on the real fixture) — structural chars in real JSON objects land roughly every 10-20 bytes, so most searches resolve inside the first 16-byte chunk, paying fixed vector setup cost without ever reaching a span where wider scanning helps; the same failure mode an earlier `ndjson.zig` fast-path attempt hit. (2) Switching to 4 separate `std.mem.indexOfScalarPos` calls (stdlib's tiered SIMD, which DID win for that earlier `ndjson.zig` case) was worse still — a genuine quadratic blowup, not just slower: the fixture has zero backslashes anywhere, so a `\` search from any position scans to the end of the current ~1MB buffer EVERY time it's called, and it's called on every structural hit (~every 15 bytes) — roughly `(buffer_size / 15)` full-buffer scans per buffer, which never finished inside a 60-second timeout. Reverted both times back to the plain scalar per-byte scan, which measured a real, stable ~20% speedup on its own (single-thread 4.60-4.73s → parallel 3.77-3.80s) — smaller than CSV/NDJSON's parallel wins, consistent with the boundary walk itself remaining a real, unavoidable sequential cost, but a genuine improvement over the single-threaded-delegation version M9 originally shipped. Full Zig/Python/Node/C-ABI suites re-verified green.

**M13 — `negate`: the complement of a WHERE clause.** One flag on `QueryOptions`, carried through every filter path in the library. `NOT(p1 AND p2 AND ...)` — the negation of the whole conjunction, not a general boolean expression.

That distinction is the entire design, and it is what kept this small. The motivating question was "which rows FAILED these checks", which is the complement of a result set, not an arbitrary predicate tree. Answering it with general OR would have meant an expression tree in `query.zig`, a nested representation across the flat-array C ABI (`scanio_predicate_t` is a `const scanio_predicate_t *` plus a length, and has been since M3), and a real grammar in the WHERE parser — closing the documented M5a "no OR" gap as a prerequisite to shipping anything. Instead: `matches()` returns `m != negate`, and the flat AND-list stays flat. The M5a gap is not closed by this and is not claimed to be; it is sidestepped, because the case that actually needed it did not need OR.

Measured motivation, not a hypothetical. On a 186MB/3M-row CSV where ~1% of rows fail a four-rule schema, pulling the failing side costs **0.18s** and pulling the passing side costs **16.2s** — the rejects are the small side by two orders of magnitude. `validate_iter()`, which streams every row into Python to hand back the 1%, measured 14.5s; the same partition expressed as `scan_array(where=..., negate=True)` is ~80x cheaper because the expensive half never crosses the FFI boundary at all. That measurement is what motivated the flag; the follow-up work to express validation rules as predicates builds on it.

Two semantics chosen deliberately, each because the alternative is a silent wrong answer rather than an error:

- **No `where` at all matches nothing.** The negation of "keep everything" is "keep none". Both `Query.count()`'s newline-only fast path and `parallelCountRowsWhere()`'s bare-count shortcut would otherwise answer with the row total, and the Python client had a third such shortcut (`_open_filtered` skips building options entirely when there is no filter and no extra column). All three are now guarded, each with its own test, because each was a separate opportunity to return the exact opposite of what was asked.
- **A row too short to hold a predicate's column counts as rejected.** It cannot satisfy `amount >= 0`, so it belongs with the rejects rather than falling out of both halves. This falls out of `matches()` already returning false for a missing column, but it is the behaviour an import wants and is tested as such, not left as an accident of implementation.

`matches()` takes `negate` as a required argument rather than a defaulted one, on purpose: there are eight filter paths (CSV/NDJSON/JSON-array x count/scan/columnar, plus the serial `Query`), and a defaulted parameter is exactly how one of them silently keeps returning the wrong half. Every worker context and worker struct in `parallel.zig` carries the field beside its `predicates`, so the two cannot be separated.

C ABI: `negate` is the LAST field of `scanio_options_t`, so a caller that zero-fills the struct — every existing one does — keeps its current behaviour without knowing the field exists. `scanio_parallel_collect_columnar()` gained an explicit parameter, which is a signature change; acceptable pre-release, and preferable to a second entry point.

Surface: Zig (`QueryOptions.negate`, `parallelCountRowsWhere`/`parallelScan`/`parallelScanColumnar`), C ABI, Python (`scan`/`scan_array`/`scan_table`/`count`), Node (`scan`/`scanArray`/`count`), CLI (`--not`), MCP (`scan`/`count`). `--not` is refused alongside `--validate`, which has its own `--valid`/`--invalid`, rather than becoming a second silently-ignored way to say the same thing.

Verified: 9 new Zig tests (serial, all three parallel engines at 1 and 4 threads, both no-filter shortcuts, projection/limit composition, NDJSON and JSON-array parity, and `matches()` as XOR directly), 2 C ABI tests including the zero-filled-struct compatibility case, 13 Python and 12 Node binding tests through the real dlopen()/N-API paths, and 373 new `zig build diff-test` checks (353 -> 726) running the whole existing QUERIES matrix inverted through an independent oracle and all three clients. The property those checks assert is not just agreement but **partition**: for every query, `|kept| + |rejected| == |total|`, with no row in both halves — plus the same for `count()` and for `scan_array()`'s separate parallel/columnar engine. The oracle was perturbed on purpose to confirm it fails when the implementations disagree (53 failures), not merely that it passes.

The flag itself is free: `--count --where` 0.370s vs `--count --where --not` 0.348s on the 186MB fixture (within noise), peak RSS identical at 10.1MB. Streaming the complement is slower only because it writes 2.97M rows instead of 30,000 — output volume, not filtering cost.

## Benchmarking discipline

Correctness must be verified before any performance claim. Datasets: 10 MB / 100 MB / 1 GB / 10 GB. Scenarios: full scan, single-column projection, multi-column projection, filter at 50%/1% selectivity, `LIMIT 10`, `COUNT`, `SUM`, `TOP 10`. Measure rows/sec, MB/sec, memory, and time-to-first-row — not just throughput.

**Real external comparison: Node's own JSON stack, same task (count `trip_id > 500000`) on the real taxi-fixture JSON array.** At a 140MB/100K-object subset (small enough that Node's native JSON.parse can actually run it): libscanio 0.36-0.38s/16.8MB, V8's native `JSON.parse` 0.59s/715MB, the `simdjson` npm binding (real C++ simdjson via N-API) 3.34s/1.65GB — libscanio faster AND far leaner than both. At the real 1.47GB/1M-object scale, native `JSON.parse` doesn't just lose, it can't run at all — `ERR_STRING_TOO_LONG` (V8's string-length cap), after already burning 3.6GB attempting to read the file into one string.

Two findings worth keeping, not just the numbers: (1) full materialization is the actual cost driver, not parsing speed — Node's JSON tools all load the whole file into one string then build a JS object per record, so memory scales with file size regardless of how fast the byte-level parsing is, and hits a hard wall well under 2GB. libscanio never does either (chunked reads, C-land row buffers, only matched rows cross into consumer memory) — that's why it wins on speed too, not just memory. (2) A fast native library doesn't imply a fast binding — `simdjson` wraps the fastest JSON parser that exists and still lost to plain `JSON.parse` by ~6x, because the N-API marshaling boundary plus still-necessary JS object construction ate the SIMD advantage entirely. Same root cause, different ecosystem, as this session's own koffi-vs-ctypes findings on the Windows Node work (M5b) — the binding layer, not the parser, was the bottleneck both times.

## N-way concurrency experiment (per-query memory under concurrent load)

Motivated by an outside-eye question ("what's the actual research angle here, not just 'fast CSV parser'?"): every benchmark in this file up to now measured ONE query at a time — the traditional single-analyst-one-big-query shape every CSV/DB benchmark is built around. Agent tool-calling is structurally different: many independent, small, frequent queries, often concurrent (a fleet of agents, parallel subagent tool calls, many sandboxed sessions sharing one host). Peak memory for ONE query doesn't answer "how many of these can run at once on a memory-constrained host" — that's a different, unmeasured axis. Real experiment, not assumed: launch N independent, single-threaded processes simultaneously (each unaware of the others, `threads=1` on both sides to isolate memory scaling from CPU-parallelism confounds), measure peak COMBINED RSS across all N plus total wall time, N = 1/2/4/8/16/32. Real 500MB slice of the real `~/code/sieswi/fixtures/ecommerce_10gb.csv` fixture (`/tmp/bench_500mb.csv`, 6.22M rows, warm page cache both sides). Correctness verified first and under real concurrency (`matches=1244118` from every process, every N, both tasks).

**Task 1 — bare WHERE-filtered count** (`libscanio`'s `filter_bench`, single-threaded): scales ~linearly in memory as N grows (expected — N independent processes), staying at a tiny per-process constant (~2MB/query even under load, N=32: 65.0MB combined RSS, 2.65s).

**Task 2 — materialized filtered scan** (`libscanio`'s `scan_bench.zig`, new: single-threaded, duplicates every matching row's fields into memory — same cost class as `scan_array()`/`scanArray()`, NOT the bounded-memory `count()`/streaming `scan()` path):

| N | libscanio wall / combined RSS |
|---|---|
| 1 | 0.82s / 276.1MB |
| 2 | 0.91s / 367.0MB |
| 4 | 1.17s / 722.7MB |
| 8 | 1.30s / 1,057.2MB |
| 16 | 2.17s / 1,944.2MB |
| 32 | 4.90s / 2,756.0MB |

**This surfaced the more important finding of the two, not a footnote**: libscanio's wall time degrades badly under load (0.82s → 4.90s, ~6x). Root cause, consistent with what this codebase's own doc comments already say (`scanArray()`'s doc comment in `node/lib/index.js`: "not memory-bounded"): materializing EVERY matching row means duplicating it past the reused scan buffer — real, unavoidable memory cost that scales with (matches × N), same as any engine would pay.

**Earlier conclusion in this section was wrong — corrected below, not deleted, since the wrong turn and why it was wrong is itself the useful record.** Pushed back on directly ("this doesn't make sense, you're not trying hard enough — check csvql or use mmap") rather than accepted. The reversal above was real as MEASURED, but the measurement compared the wrong things: `scan_array()`/`scanArray()` used a SINGLE-THREADED C ABI path (`scanio_collect()`), and — a genuinely surprising find — `parallelScan()`/`parallelCountRows()` (M9's own multi-threaded engine, already built and tested this session) were **never exposed via the C ABI at all**, not even re-exported from `root.zig`. Every "libscanio under concurrency" number measured before this point was N separate single-threaded processes, never libscanio's actual multi-threaded capability.

Checked csvql's own `src/parallel_mmap.zig` for prior art, as asked: its default parallel mode (`use_parallel_output`, whenever there's no LIMIT/DISTINCT) doesn't build an intermediate array of row objects at all — each worker thread serializes matching rows DIRECTLY into its own growing output buffer (CSV or JSON text), concatenated at the end. Its mmap path (reserved for LIMIT/DISTINCT, which need global ordering across workers) builds rows as zero-copy slices straight into the mapped file — no field-byte duplication at all for that case. Two real, different lessons taken from this: (1) avoid materializing an intermediate representation you're just going to serialize anyway; (2) zero-copy field references are possible when the source data outlives the result (mmap), not possible for libscanio's own chunked-read model without a matching architecture change (not attempted here — mmap reintroduces the exact peak-RSS-tracks-file-size problem M1 exists to avoid, a real tradeoff, not free).

**Fixes made, in order:**

1. **Re-exported `parallelScan`/`ScannedRows` from `root.zig`** — the actual gap that made the C ABI unable to reach them at all.
2. **New C ABI: `scanio_collect_columnar()` / `scanio_parallel_collect_columnar()`** — a genuinely different, more compact wire format than `scanio_collect()`'s NUL-separated row-major buffer: per-column `(data, offsets)` pairs, `offsets` a `u32` array — exactly Apache Arrow's own `StringArray` layout, on purpose. `scanio_parallel_collect_columnar()` drives `parallelScan()` (the real multi-threaded engine) instead of a single-threaded `Ctx`/`Query` loop, then repacks its `OwnedRow` results into the same columnar shape — one, not two, downstream unpacking code paths regardless of which collector produced the result. Verified: exact-match correctness against the single-threaded `scanio_collect_columnar()` on a real multi-thread-boundary-crossing fixture (row SET equality, since worker-range concatenation order isn't guaranteed to match the single-threaded scan order — a real, intentional, documented difference, not a bug).
3. **Real numbers, pure Zig, no Python/Node at all** (`parallel_bench`'s new `materialize` mode, real 50MB slice, same real e-commerce fixture): N=1 **0.05s/15.0MB**, N=8 **0.20s/378.4MB**, N=16 **0.25s/735.8MB**, N=32 **0.47s/894.8MB** — flat, low per-process cost even with heavy thread oversubscription (32 processes × ~12 threads = 384 threads on 12 real cores). This is the number that should have been measured before concluding libscanio "loses" on materialized scans — it doesn't; the earlier binding did.
4. **Wired into Python's `scan_array()`** (default path whenever `columns`/`limit` are both unset — those two still fall back to the single-threaded path, since `parallelScan()` doesn't support projection or a row limit yet, a real current scope gap, not silently wrong). Real, measured win: 0.67s/154.3MB → **0.33s/145.2MB** for a single call. Under N-way concurrency, though, a SECOND bottleneck surfaced, distinct from the collection engine: isolated by comparing a raw C ABI call (no Python object construction) against the full `scan_array()` wrapper at the same N — the raw call scales gracefully (threads=2 and threads=0/auto within noise of each other, ~2.8-2.9s at N=32, no blowup), but the full wrapper hit 7.77s at N=32. The gap is Python's OWN list/tuple construction step (`decode()` + `zip()` + list-building) running after the fast C call returns — pure Python bytecode, and it scales badly under N-way concurrent memory pressure, same mechanism as the `scan_bench.zig` finding above, now cleanly isolated to a specific, smaller piece of code instead of "materialization in general."
5. **Built `scan_table()`** — a `pyarrow.Table` constructed via `pa.Array.from_buffers()` directly over the SAME `(data, offsets)` buffers, zero Python object construction per cell at all (only lightweight Arrow array wrappers). Real lifetime-management subtlety, handled explicitly: the C-side buffer must outlive every Arrow object referencing it, but must eventually get freed — solved with `pa.foreign_buffer(address, size, base=handle)`, where `handle` is a small Python object wrapping the raw `cc` pointer with a `__del__` that calls `scanio_collect_columnar_close()`; pyarrow's own refcounting on `base=` (not this function returning) decides when that actually runs. Verified: correct data end-to-end (every value, first row, last row, unique-value check), and no crash/dangling-pointer access after explicit `del` + `gc.collect()`. Real numbers: single-call 145.2MB → **99.1MB** (32% less); under N-way concurrency, dramatically better than `scan_array()`'s blowup (N=32: **3.26s/3246.0MB** vs `scan_array()`'s 7.77s/2590.1MB) — but still behind the pure-Zig number (0.47s/894.8MB). That remaining gap is Python interpreter/process-startup overhead itself under N-way concurrent process load, not anything in libscanio's Zig core — a real, separate, currently-open cost.
6. **Wired into Node's `scanArray()`** too, same shape (default path when no `columns`, delegates to `scanio_parallel_collect_columnar()`, decodes per-column buffers via `Buffer.toString('utf8', start, end)` instead of one big NUL-split). Real, measured win: 0.69s/171.3MB → **0.43s/173.8MB** for a single call (~38% faster, memory roughly unchanged — same "V8's own object overhead dominates memory, not the collection engine" story as Python). Under concurrency: N=32 **4.00s/4330.2MB**, same class of remaining gap as Python's `scan_array()` (pre-`scan_table()`-fix) — no Node equivalent to `scan_table()`'s Arrow zero-copy path built yet (a real, logged next step, not attempted here).

All of this verified against the full test suite at every step (78 Zig, 52 Python, 53 Node, 10 C-ABI smoke), not just the new-feature-specific checks.

**Sharper thesis, corrected**: the earlier "prefer streaming over bulk-materialize" recommendation was too broad — it was true for the SPECIFIC bindings measured at the time (which weren't using libscanio's actual multi-threaded engine), not a fundamental property of materialization itself. libscanio's real multi-threaded materialized scan is genuinely strong on its own terms. The honest, narrower, still-open gap is entirely in the LANGUAGE BINDING layer under high concurrent PROCESS load (Python/Node interpreter overhead, object-model cost, process-startup cost) — not in libscanio's Zig core, which the pure-`parallel_bench` numbers prove out cleanly. Closing that fully would mean either a Node-side Arrow/typed-array equivalent to `scan_table()`, or accepting that very-high-N concurrent SEPARATE PROCESSES (as opposed to one process serving many agent requests, e.g. via a long-lived MCP server process) will always carry real interpreter-startup cost no matter how fast the underlying engine is.

**MCP's own `scan` tool was checked separately and had the exact same gap** — it called `list(libscanio.scan(...))` (the single-threaded row-at-a-time generator, drained in a Python loop), never `scan_array()`, so none of the fixes above actually reached the tool an agent calling this MCP server would use. Fixed: `scan` now calls `scan_array(..., as_dict=True)` directly, which gets the same automatic dispatch (parallel engine when `columns`/`limit` are unset, single-threaded fallback otherwise) for free. Verified through the real `call_tool()` path, both branches: unfiltered-columns call (124,095 correct rows, real 50MB fixture) and the `columns`+`limit` fallback call (3 correctly-projected rows). `README.md`'s "Status" line was also stale — hadn't mentioned `order_by`, `describe`, the parallel scan path, or `scan_table()` at all; updated to reflect what's actually shipped.

7. **`scanio_parallel_collect_columnar()`'s remaining double-copy eliminated.** Even after fix 2 above, that C ABI function still called `parallelScan()` (which builds `OwnedRow` — one `allocator.dupe()` call PER FIELD, millions of tiny allocations for a large result) and then manually re-copied every field a second time into the columnar `(data, offsets)` buffers — correctness-first, not the real fix. All 94 Zig tests, 52 Python, 53 Node re-verified green.

## Honest gaps

Named directly, not left implicit — asked for an outside-eye assessment of the project and these are the real weak points that came out of it, not resolved yet:

- **`scan_bench`'s wall-time degradation under N-way concurrent load was investigated, not left as an open mystery — root-caused to real host memory pressure, with a real methodological caveat attached.** `vm_stat` before the N=32 run showed only ~68MB genuinely free on the test machine (a live interactive dev box — multiple Claude Code sessions, VS Code, Safari, Teams, Brave, WhatsApp all running, not a dedicated/idle benchmark host); during the run, real swap activity occurred (+44,972 pages swapped in, +279,624 swapped out, ~4.4GB moved through swap). Cross-checked at 1/10th the data (a 50MB slice instead of 500MB): the SAME degradation pattern appeared at a smaller absolute scale (0.11s → 0.51s, ~4.6x, vs 500MB's 0.82s → 4.90s, ~6x) — ruling out "one bad run" and confirming the pattern is real, not noise. Mechanism: materializing every matching row means real memory demand that scales with (matches × N), so libscanio's per-process footprint grows with N and is directly exposed to whatever memory pressure exists (from the N siblings themselves, or from everything else running on a shared/busy host). This is the SAME root cause as the memory-total finding, not a separate mystery — and it's consistent with, and mechanistically explains, why `scan_array()`/`scanArray()` are already documented elsewhere in this codebase as "not memory-bounded." Honest caveat: this experiment ran on a busy interactive machine, not a dedicated/idle host — the absolute numbers would likely look better on a quieter box, but the underlying mechanism (bulk materialization's memory cost determines its exposure to memory pressure, streaming architectures are more insulated from it) would hold regardless of host business, since it follows from what each engine actually does, not from this specific run's noise.
- **No fuzzing anywhere.** Every correctness check in this project so far is either a hand-written unit test or a comparison against a real fixture — none of it is property-based/fuzz testing (random/adversarial CSV, NDJSON, or JSON-array input hunting for parser crashes, infinite loops, or silent wrong answers). Given how much of this codebase is hand-written state machines over byte streams (CSV/NDJSON/JSON-array boundary tracking, parallel range-splitting), this is the highest-value gap to close next.
- **JSON-array parallel path is under-tested on shape diversity.** Every real-scale benchmark and correctness check for `parallel.zig`'s JSON-array code ran against fixtures with zero escaped characters (no `\"`, no `\\`) — the escape-handling branches (`skip_next_byte` carrying an in-progress escape across a chunk boundary, `isEscapedAt`-based backslash-parity checks) are covered by small unit tests but never exercised at real multi-GB scale or under real-world messy data (user-generated text fields with actual escapes, unicode, etc.).
- **RESOLVED — Windows Node crash. koffi replaced with a real N-API addon, not patched.** `scanio_open()` crashed through koffi on Windows (see M5b) — three theories tried (struct layout, null options pointer, koffi version upgrade to 3.2.1), all disproven; a targeted diagnostic narrowed it to koffi's own Windows FFI dispatch for 2-argument/pointer-arg/`void*`-return calls specifically, confirmed NOT a libscanio bug via an identical-shape call through Python ctypes passing cleanly on the same runner. Unfixable from this side (koffi's own internals), so replaced koffi entirely rather than waiting on an upstream fix: `src/node_binding.zig` compiles directly against Node's `node_api.h` (same pattern csvql, this project's sibling, already uses), no dynamic-FFI layer at all. Full API surface ported (`scan`, `scanArray`, `schema`, `count`, `aggregate`, `topk`, `orderBy`, `profile`, `describe`) with 100% parity verified against the exact pre-existing test suite (53/53 pass, identical results). Verified Windows-first on real CI (all three platforms green, `windows-latest` checked before macOS/Linux, deliberately, given how this bug was found last time). koffi is no longer a dependency anywhere in this project — zero runtime npm dependencies now. `node/`'s WHERE-string parsing also moved from JS regex into Zig (`src/where_parser.zig`), with real adversarial test coverage a straight port never got (operator-substring-in-value, empty WHERE, malformed IN clauses) — caught one real pre-existing memory leak in `parseColumnsJson`'s error path immediately on the first test run.

**Outside-eye review of this whole migration found real gaps — closed them, not just acknowledged them:**

1. **Handle-safety fix, real not cosmetic.** Streaming `scan()`'s open/next/close used the Query's raw heap pointer, cast to a JS number, as the handle — a garbage, stale, or double-closed handle would `@ptrFromInt` it and read/write through arbitrary memory. Replaced with `handle_registry`, a mutex-guarded `AutoHashMapUnmanaged` keyed by a small monotonic ID, not the address. An invalid handle now fails with a normal JS exception; double-close is a safe no-op (matches the old contract's implicit behavior, made explicit and tested). 5 new regression tests, including one that reuses a handle after `closeScan()` and confirms it throws instead of touching freed memory.
2. **Real adversarial WHERE-parser tests, not just a ported suite.** Split the parser into its own file (`src/where_parser.zig`, importable without Node headers) with 19 new `zig build test` cases covering things the straight port never exercised: a value containing an operator-looking substring (`name = a>b`, must not misparse at the embedded `>`), malformed IN clauses, empty WHERE, unknown columns. One of these — `parseColumnsJson`'s error path — found a real, pre-existing memory leak on its very first run (fixed with one `errdefer`).
3. **Performance methodology bug caught and fixed before it shipped a false conclusion.** Set out to get an honest koffi-vs-N-API number (a real gap the initial port skipped). First measurement looked damning — N-API's `count()` was 7x slower (330ms vs koffi's 45ms) on an identical WHERE-filtered query. Investigated rather than accepted: (a) found `countWork`/`aggregateWork` never wired `QueryOptions.stop_after_column` the way the old koffi `openFiltered()` did — a real, now-fixed omission (`where_parser.maxPredicateColumn()`), safe specifically because `count()`/`aggregate()` never return row data, unlike `scanArray()`/`topk()`/`orderBy()`, which stay unbounded on purpose (bounding those would silently truncate returned rows, same reasoning the old koffi code documented). That closed part of the gap (330ms → 275ms) but not most of it. (b) Root-caused the rest by profiling raw `Query.count()` in isolation (no N-API, no binding at all) — same 275ms, proving the binding wasn't the cause. (c) Found the real bug: **the N-API addon had been built and benchmarked as a Debug build the entire time** (`zig build node` with no `-Doptimize=ReleaseFast`) — a pure testing-methodology mistake on my part, not a shipped defect (the actual `node/package.json` build script always passed the flag correctly). Rebuilt in ReleaseFast: `count()` landed at 43-47ms, matching koffi's 42-63ms almost exactly, N-API using slightly less memory (38-39MB vs 42-43MB).
4. **A genuinely surprising, unplanned finding from setting up that comparison: koffi's own `scanArray()` crashes reproducibly on macOS/arm64 (SIGILL, exit 132, 3/3 runs), not just on Windows.** Discovered by checking out the last koffi commit (`8c93994`) in a worktree to get a real baseline — `schema()`/`count()`/`aggregate()` all worked fine through koffi on this host, but `scanArray()` (the parallel-collect path) crashed silently every time, no catchable JS exception, same failure signature (silent native crash, not a normal error) as the documented Windows bug. Never chased further — koffi is already deleted and this isn't a libscanio bug to fix — but it's real, first-hand evidence that koffi's fragility wasn't Windows-specific, strengthening rather than just assuming the case for having replaced it. N-API's own `scanArray()` on the identical query: 174-194ms, reliable, every run.
- **xan/qsv/pyarrow/csvql comparisons are spot checks, not a systematic differential test suite.** Real and valuable (caught 3 real bugs this session — the O(n²) header lookup, an NDJSON off-by-one, a dangling-slice UAF), but they're one-off comparisons on 2-3 real fixtures, run manually, not an automated property-based or randomized differential testing harness (generate N random queries, run against both engines, diff results) that would catch classes of bugs the manually-chosen comparisons happen not to exercise.
- **Benchmark numbers aren't statistically rigorous.** Most measurements in this file are 2-4 manual runs on one machine, reported as a range or a single representative number — real, not fabricated, but not the same rigor as multiple hardware configs, formal variance/confidence intervals, or an automated benchmark-tracking harness that would catch regressions over time.

**Root-caused one real, fixable piece of the gap — `parallelScanColumnar()`'s own merge step, not just "libscanio has overhead."** Measured actual result-data size via `tbl.nbytes`/`tbl.column(i).nbytes` on both sides for the same 500MB/1.24M-row query: libscanio's real output is 131.5MB, pyarrow.dataset's is 118.5MB (close — the small gap is pyarrow's typed int64/timestamp columns vs libscanio's all-string output, a separate, smaller effect, not investigated further here). But libscanio's peak RSS was 534-543MB — roughly 400MB of overhead above the actual result, well beyond pyarrow.dataset's own ~180MB overhead (298-315MB peak minus 118.5MB data). Found one real cause: `mergeColumnarWorkers()` copied every worker's fully-populated `ColumnBuf` into a fresh final buffer via `appendSlice`, but the caller (`parallelScanColumnar()`) held ALL workers' buffers alive via `defer` until the whole function returned — so every worker's buffer and the growing final buffer coexisted simultaneously at merge's peak, not released incrementally. Fixed: `mergeColumnarWorkers()` now frees each worker's buffer immediately after its data is copied into `final_columns`, instead of the caller deferring all worker cleanup to function exit. Correct, tested (full 94 Zig / 52 Python / 53 Node suite green), but the real-world improvement was small — 534-543MB before, 518-535MB after, roughly 1-3%, not the fix this gap needed.

**Isolated further, via the raw C ABI directly (no Python/pyarrow wrapper involved at all):** even completely single-threaded (`num_threads=1`, so no cross-worker merge duplication at all beyond one worker), peak RSS was still 493MB against the same 131MB of real output — a 3.7x ratio that has nothing to do with thread count (427-505MB measured flat across 1/2/4/12 threads). The real remaining cost: each worker (even just one) still builds its OWN buffer via `ArrayList`'s doubling-growth strategy (real overshoot: capacity can run up to ~2x the final content size before growth stops), and that worker buffer stays alive while `mergeColumnarWorkers()` copies it into a SEPARATE, independently-growing final buffer — worker buffer and final buffer both fully sized and coexisting at the moment of copy, even with the eager-free fix above, because the eager-free only fires AFTER a worker's copy completes, not during it.

**Done — two-pass exact-sized merge, per the plan above.** `mergeColumnarWorkers()` now sums each worker's already-known byte/row counts first (no second file read — every worker already finished scanning by this point, so its counts are already in memory), reserves `final_columns`' buffers at EXACT final size via `ensureTotalCapacityPrecise()`, then bulk-copies with `appendSliceAssumeCapacity()`/`appendAssumeCapacity()` — no growth-doubling overshoot on the final buffer at all, on top of the earlier eager-free fix for worker buffers. One real bug caught by the test suite immediately: `newColumnBufs()` already appends the leading `0` offset via a regular `append()`, and the first version of this fix appended it a SECOND time before reserving exact capacity — an off-by-one that overflowed the precise-capacity assert on the very first correctness test run, not silently wrong. Fixed (removed the duplicate append), full suite (94 Zig / 52 Python / 53 Node) green after.

Real numbers, reported as measured, improvement AND regression both — not just the flattering half:

Same 500MB fixture, single call, 3 runs: **534-543MB → 397-398MB** (~26% reduction) — the two-pass rewrite genuinely worked where the eager-free-only fix (1-3%) mostly didn't. Isolated via the raw C ABI directly (no Python/pyarrow involved): single-threaded peak dropped from 493MB to 451MB, and the flat-across-thread-count pattern held (338-451MB across 1-12 threads, vs 427-505MB before).

N-way concurrency sweep (50MB fixture, same harness), reran twice to check reproducibility: N=1 improved (101.6MB → 87.8-88.0MB), but **N=32 got WORSE, consistently across both reruns (1,968.3MB before → 2,087.9MB and 2,292.4MB after)** — a real, reproducible regression at high concurrency, not noise (checked `vm_stat` swap deltas, negligible on all three runs).

**Root-caused, not left as a guess — and the fix for it made things WORSE again, twice, before landing on reverting entirely.** The actual cause: reserving every final column at its FULL final size up front (`ensureTotalCapacityPrecise` for all `n_cols` columns, in a loop that finishes BEFORE any worker gets freed) guarantees a moment where every worker's fully-populated buffer AND every final column's fully-reserved buffer exist simultaneously — a real, structural 2x peak, strictly worse than the growth-based approach it replaced (which freed early workers progressively while later ones were still being copied, so never hit a full-duplicate peak across ALL data at once). Tried to fix that by growing each final column to its EXACT running total after every worker instead of reserving everything up front (no upfront full-size reservation, no doubling overshoot either) — measured WORSE than both prior versions on single-call memory (557-588MB, worse than the very first appendSlice-based baseline of 534-543MB): `ensureTotalCapacityPrecise`'s growth calls use realloc-style move-and-copy when growing past current capacity, so each of the ~12 exact-growth steps briefly holds the old (smaller) and new (larger) buffer simultaneously too — doing that repeatedly compounded into a bigger peak than either single-shot approach.

**Reverted `mergeColumnarWorkers()` entirely back to the original doubling-growth `appendSlice` approach** (the one from the double-copy fix earlier in this section), keeping only the eager-free-each-worker-immediately change (the one part of this whole investigation that was unambiguously safe — it can only free memory sooner, never change the growth pattern that caused either regression). Verified back to the known-good numbers: single-call 508-540MB (matches the pre-two-pass baseline), N=32 combined RSS 2,035.3MB (matches the original 1,968.3MB within normal run-to-run variance — this particular rerun hit some real swap activity, 21,020 pages out, consistent with the memory-pressure caveat already established elsewhere in this file, not a code regression). Full suite (94 Zig / 52 Python / 53 Node) green.

**Net result of this whole detour: no memory win, no memory loss, back to where fix 7 left off — but two real, now-documented dead ends that won't be re-attempted blind.** The actual remaining gap vs `pyarrow.dataset` (298-315MB vs libscanio's ~510-540MB at 500MB scale) is still open. A real fix would need workers to write directly into a SHARED final buffer during the scan itself — true two-pass over the FILE (count matches first without storing data, then write at precomputed offsets, no per-worker intermediate buffer at all) — not the single-scan-then-reshuffle approach both failed attempts here were variations of. That's a genuinely different, bigger design.

**Decided not to pursue it — a settled call, not an open item.** Raised directly: shouldn't libscanio at least match Arrow on this single-call metric, since it's doing objectively less work per row (no type system, no schema negotiation, no batch machinery)? Fair question, and the honest answer is: in principle yes, in practice this is a real, unresolved gap — but the settled framing going forward is that Arrow/`pyarrow.dataset` is a complete columnar analytics stack and libscanio is a thin scanner; losing to a full analytics engine on the ONE task it's built entirely around (materializing a typed result set) is expected, not a defect worth a third risky rewrite after two already regressed real measurements this session. The caveat that keeps this honest, not just convenient: this concession applies ONLY to single-call full materialization. It does NOT apply to the N-way concurrency result a few paragraphs up, where libscanio won at every N against both pyarrow paths (2.0GB vs 4.6-5.6GB combined RSS at N=32) — that gap isn't "Arrow does more work per call," it's Arrow's fixed per-process overhead multiplying under concurrent load, which is the actual structural claim this project's thesis rests on. Concede single-call materialization. Hold the concurrent-load memory line — that one still needs defending, not excusing.

**Tried a cheaper alternative first — typed columns instead of a merge rewrite — and it's a real, honest negative result on memory, though a real positive on correctness/ergonomics.** Part of pyarrow.dataset's smaller footprint is real type inference: `quantity`/`price_minor`/etc. come back as int64/timestamp (8 bytes/value, fixed-width), not offset+string bytes. Added `scan_table(path, where=None, infer_types=False)` — when `True`, columns `describe()` classifies as integer/float/boolean/datetime get cast via `pyarrow.compute.cast()` to a real typed Arrow array (int64/float64/bool/timestamp[s], with a tz-aware/tz-naive fallback pair for the two real ISO8601 shapes `describe()` lumps under one "datetime" label), matching `pyarrow.dataset`'s own inferred schema exactly on the shared fixture. Sample-based inference can be wrong for data outside `describe()`'s sample — a cast failure on the real data falls back to keeping that one column a string, silently, rather than raising; the rest of the columns still get cast. 7 new tests added (typed round-trip, boolean correctness, the string-fallback path with a real fixture where the 1001st row breaks the 1000-row sample's inference), all passing.

**Measured the actual memory effect before believing it would help — it made things WORSE, not better: 508-540MB baseline → 553-589MB with casting on.** Root cause: `pc.cast()` allocates brand-new typed buffers, but the original string source bytes can't be freed per-column — all columns share one C-side context (`cc`), closed as a single unit only once every column's Python wrapper is gone, not per-column. So casting adds new typed memory ON TOP of the string data instead of replacing it. A real memory win here needs Zig itself to emit typed buffers during the scan (the bigger, not-yet-attempted design noted above), not a post-hoc Python-side cast. **Defaulted `infer_types` to `False`, deliberately** — the feature is real value for correctness/ergonomics (typed output usable in pandas/numpy without a manual cast, matches what a reasonable caller would expect from a "give me a real Arrow table" API), but is NOT a memory optimization, and defaulting it on would have silently regressed `scan_table()`'s already-established, already-benchmarked memory profile for every caller who didn't ask for it — confirmed the default path still measures 513-534MB, matching the pre-existing baseline, no regression.

Outside-eye grading of this project as CS research landed at C+: solid engineering, well-understood techniques, no new algorithm or data structure — not a systems-novelty paper. The realistic path to a defensible A-/B+ isn't inventing new CS, it's turning the per-query-memory-under-concurrency angle (see the N-way concurrency experiment section above) into a rigorous evaluation/methodology contribution — the kind DaMoN and similar venues credit even without a new algorithm. Concrete, ordered work, not done yet:

1. **Name and formally define the metric.** "Peak combined RSS under N-way concurrent load" isn't an established, citable benchmark dimension — every existing CSV/DB benchmark (including this project's own `docs/BENCHMARKS.md`) measures one query at a time. Write a precise definition and state exactly what single-query peak-RSS benchmarks structurally miss.

Two of the three pieces this needs are already solved by tools this project doesn't currently depend on: **[hyperfine](https://github.com/sharkdp/hyperfine)** (cross-platform, warmup runs, mean/stddev/min/max, JSON export — the standard tool for exactly this class of CLI wall-time comparison) for single-process timing, paired with the OS's own `/usr/bin/time -l` (macOS) / `-v` (Linux) for single-process peak RSS instead of a custom polling loop. Neither of those covers the one genuinely novel piece — peak COMBINED RSS across N concurrent separate processes — because no established tool measures that shape of workload; that part stays a small custom harness, which is itself supporting evidence the metric is under-tooled, not just under-benchmarked. For fuzzing: Zig 0.15 ships a native, coverage-guided fuzzer in-toolchain (`zig build test --fuzz`, `std.testing.fuzz`) — use that directly instead of writing or vendoring a bespoke fuzz harness or reaching for AFL++/libFuzzer glue.

Reframed claim, falsifiable and generalizable past this one engine: **general-purpose analytical engines carry fixed per-process resource-reservation overhead that's invisible in single-query benchmarks (because it's a constant, not a function of query cost) but multiplies linearly under N-way concurrent PROCESS load** — a structural cost of being built for one-analyst-one-big-query, not a bug, and not a cost a special-purpose scanner needs to pay. Testable next step, not yet run: hold query complexity fixed and vary result-set size across a wider range to find where the floor stops being flat — not yet done, would make this a real, falsifiable, checked claim instead of an inference from the numbers already collected.
5. **Release the harness + fixtures as a reusable artifact**, not numbers trapped in this markdown file. Artifact-track credit is real at DaMoN-adjacent venues and is cheaper to earn than a new algorithm.
6. **Close the credibility-undermining gaps first**, specifically the ones already logged below under Honest gaps: no fuzzing anywhere, JSON-array escape-path under-tested at scale, benchmark numbers not statistically rigorous. A rigor-focused paper submitted while those are still open contradicts its own thesis.

Not started except the mechanism reasoning above (item 4), which is real analysis, not a placeholder. Real remaining cost: weeks of evaluation-design and multi-host measurement work, not a quick follow-up — logged here so it isn't lost, not because it's imminent.

  or narrow projection where other engines' columnar scan already does
  minimal work.
- `validate_report()`: no other engine here has an equivalent built-in
  feature (schema rules — `min`/`max`/`required` per column — not just
  type casting), so the only real comparison is a naive hand-rolled
  Python loop doing the same four checks: 0.391s vs 5.920s, 15.1x faster,
  both agreeing exactly on which 58 of 1,000,000 rows were invalid.

**Honest summary of the whole exercise**: libscanio does not win every
shape against every engine — polars' raw column-scan speed beats it on
count-only and narrow-projection shapes. It wins decisively, both time
and memory, on the shape its actual architecture targets (selective
WHERE, full-row materialization), and wins memory by a wide margin on
every shape without exception, including the two it loses time on. That
is the honest, falsifiable version of "libscanio wins" — not "libscanio
is fastest at everything."

## Root-caused and fixed: bare `count()` was single-threaded for no reason

**The bare-count loss above wasn't a ceiling — it was a wiring gap.**
Investigated directly: pure-Zig `Query.count()` (0.047-0.059s) was
already near-identical to the Python binding's time (0.059s), ruling out
binding overhead. `src/simd_count.zig`'s newline count was already
vectorized (confirmed by reading it — `countByte()`, widest-SIMD-lane
popcount, this session's own M-something fix). Then found the real
cause: `parallelCountRows()` — a complete, already-tested, multi-threaded
row counter — has existed in `src/parallel.zig` since M9 and is even
re-exported publicly from `root.zig`, but **nothing calls it**. Not the C
ABI (`py_query_count` in `python_api.zig` always called the
single-threaded `Query.count()`), not Node's `countWork()`, not the CLI.
Confirmed by invoking it directly (temporary investigation code in
`bench_tool.zig`, reverted after measuring, never shipped): 0.011-0.028s
— already at or beating polars' 0.015s.

**Fixed by wiring it in, not by writing new counting logic.** Added
`py_count_rows_parallel()` (`python_api.zig`) + `count_rows_parallel`
method (`_api.c`), and Python's `count(path)` now dispatches to it
whenever `where is None and not negate` (the only case
`parallelCountRows()` — an unconditional, unfiltered count — can
correctly answer). Node's `countWork()` (`node_binding.zig`) got the
same dispatch. Real, measured result on the 417MB/1M-row/51-col fixture:
Python 0.059s → **0.016s**, Node 0.050s → **0.016s** — both now
essentially tied with polars (0.015s) instead of 3-4x behind, while still
using 6-17x less memory (28-51MB vs polars' 473MB). Full suite reverified
green: 94 Zig, 246+17 Python, 33+177 Node.

**Predicted this exact gap would recur elsewhere — checked, and it did.**
Audited every public entry point against what `parallel.zig` actually
builds: only 4 parallel primitives exist total (`parallelCountRows`,
`parallelCountRowsWhere`, `parallelScan`, `parallelScanColumnar`) — no
parallel aggregate/topk/orderBy exist at all, so those weren't a wiring
gap, there's simply nothing built yet to wire. But
`parallelCountRowsWhere()` — the WHERE-filtered sibling of the function
just fixed above — had the identical problem: exists since M9,
re-exported from `root.zig`, referenced only in a comment in `c_api.zig`,
never actually called by Python, Node, or the CLI. Every WHERE-filtered
`count()` call, in every binding, was single-threaded the entire time
this project has had a multi-threaded filtered-count engine.

**Measured before fixing, same discipline as before**: temporary
investigation code in `bench_tool.zig` (reverted after measuring, never
shipped) showed `parallelCountRowsWhere()` at 0.015-0.017s on the
417MB/1M-row/51-col fixture's `WHERE rate_code_id = 6` query, versus the
single-threaded path's 0.097s — a ~6x win, confirmed before spending
effort wiring it in.

**Fixed identically to the first gap — wired, not rewritten.** Node's
`countWork()` (`node_binding.zig`) collapsed entirely into one call to
`scan.parallelCountRowsWhere()` — it already handles empty predicates
(dispatching internally to `parallelCountRows()`), negate (including the
negate-with-no-predicates zero-scan case), and `stop_after_column`, so
the old single-threaded `Query.open()`/`.count()` branch had nothing left
to do. Python got a new C export, `py_count_rows_where_parallel()`
(`python_api.zig`) + `count_rows_where_parallel` method (`_api.c`),
mirroring `QueryCtx.open()`'s existing predicate-JSON-decode logic
exactly; `count()` (`__init__.py`) now probes the header for column
names, resolves the WHERE string to predicates the same way it always
did, then calls the new export instead of opening a `Query`. Verified
against an independent `awk` scan for both a single predicate and a
compound `AND` clause (19/1,000,000 for `rate_code_id=6 AND
vendor_id=CMT`), plus both negate variants. Full suite reverified green:
94 Zig, 246+17 Python, 33+177 Node.

**Real numbers**: 417MB fixture, `WHERE rate_code_id=6`: Python
0.097s→**0.023s**, Node 0.089s→**0.016s** — both now clearly ahead of
polars (0.122s) instead of roughly tied with it. At 8.5GB scale, the
fix's effect is bigger, not smaller: Python 4.03s→**1.75s**, Node
4.06s→**1.46s** — this was the one shape where duckdb (3.08s) beat
libscanio outright; it no longer does. Two real wiring bugs found and
fixed via the exact same audit-then-measure-then-connect method, not two
different investigations.

**Still open, not done in this pass**: whether `scan_array(columns=...)`
(Python) has an equivalent gap — checked directly: no, it's a real
capability gap, not a wiring one. `parallelScanColumnar()` (`parallel.zig`)
has no `columns` parameter at all — it unconditionally builds every
column (`n_cols = q.header().len`), in both its CSV and JSON-array
branches. There is nothing sitting built-and-disconnected to wire here;
adding projection support means extending the function itself. Bigger,
separate scope from the two wiring fixes above — not started.

**Dispatch-path test added, closing the "doesn't scale" gap above.**
Two instances of the same bug class (a correct, complete, multi-threaded
function sitting fully built but uncalled) were found this session by
manual audit alone — not a repeatable process. Added
`parallel_mod.debug_spawn_count`, a `pub var` incremented once inside
`spawnAndJoin()` (`parallel.zig`) — the single choke point every parallel
primitive in the file funnels through, so one counter covers all of them,
not just the two just fixed. Discovered `src/python_api.zig` needs no
`Python.h` `@cImport` at all (pure Zig, `extern "C"` boundary only), so it
was previously untested by `zig build test` for no real reason — added it
as its own test module in `build.zig` (same shape as `where_parser.zig`'s
existing Node-header-free module, re-exported `parallel_mod` as
`root.zig`'s `parallel_debug` for test-only introspection) and wrote two
tests there asserting `py_count_rows_parallel`/
`py_count_rows_where_parallel` both increase the spawn counter, not just
return the right answer. **Verified the tests actually catch the
regression they exist for**, not just that they pass: temporarily
disabled the counter increment, confirmed all three new tests (two in
`python_api.zig`, one in `parallel.zig` itself) fail, then restored it —
a correctness-only test would have stayed green through that change,
which is exactly the blind spot that let the original bug ship
unnoticed. Full suite green after: 180 Zig test blocks (up from 177),
246+17 Python, 33+177 Node.

Node's `countWork()` (`node_binding.zig`) still has no equivalent
dispatch test — it needs real Node headers to compile at all, so it
can't join `python_api.zig`/`parallel.zig` in `zig build test`; covering
it would mean exposing `debug_spawn_count` through the N-API surface
itself for `node/test/addon_test.js` to read, which pollutes a shipped
API with test-only introspection. Not done — the Node-side risk is
lower now anyway, since `countWork()` no longer has a single-threaded
branch left to regress to (see the fix above: it collapsed to one
unconditional call).

**Checked whether the 8.5GB duckdb win generalizes to a bigger scale, on
request — it doesn't hold, it reverses.** Found and used a third real
fixture, `bench/.taxi-data/trips_16gb.csv` (17GB, 40M rows, same schema),
not synthetic. Same `WHERE rate_code_id = '6'` query: libscanio 3.40s/
30.2MB vs duckdb 7.01s/460.8MB — libscanio wins both axes by roughly the
same margin as at 8.5GB, not by a shrinking one. 634/40,000,000 rows,
confirmed against an independent `awk` scan before trusting either
engine, matching all three fixtures' discipline. No case has been found,
at any tested scale, where duckdb currently beats libscanio — the 8.5GB
loss documented earlier in this file was real at the time and is now
closed by the `parallelCountRowsWhere()` fix, not superseded by a new
loss elsewhere.

## Found and fixed a third instance — the CLI's `--count`, on request

Asked directly whether anything still called the single-threaded
`Query.count()` path, since Python's and Node's bindings had both moved
off it. Answer: yes — `cli.zig`'s `--count` was the third and last
binding still calling `q.count()` unconditionally, same bug class as the
two already fixed. Fixed the same way: `--count` now calls
`parallelCountRowsWhere()` directly and skips opening the single-threaded
`Query` entirely for that path (the header probe earlier in `main()`
already resolves `--where` into predicates, so nothing else needed
opening a `Query` first). Verified against the real 417MB fixture:
`scanio file.csv --count` → 1,000,000; `--where "rate_code_id = 6"
--count` → 26; the same with `--not` → 999,974 — all correct, `user`
time (0.72-0.76s) far exceeding `real` time (0.07-0.13s) confirming
genuine multi-core parallelism, not a fluke. `zig build test`,
`diff-test` (743/743), and `smoke-test` all green after.

**One real behavior change, deliberately not preserved**: `--count`
combined with `--limit` used to cap the count at the limit (an
incidental side effect of sharing `Query.open()`'s options struct with
the row-output path, never a documented feature — no runtime test
asserted it, only argument-parsing). `parallelCountRowsWhere()` has no
limit concept, matching Python's and Node's `count()`, neither of which
ever exposed a `limit` parameter for counting. Chose consistency across
all three bindings over preserving an undocumented, untested CLI-only
quirk.

**Asked whether the now-fully-dead single-threaded count path should be
deleted — checked precisely, then removed exactly the dead part, not
the whole thing.** `Query.count()` itself (`query.zig`) stays: `c_api.zig`'s
public `scanio_count()` still legitimately calls it, and that's a real,
documented C ABI function (`include/libscanio.h`) operating on an
already-open `scanio_t` handle — a shape `parallelCountRowsWhere()`
can't serve without reopening the file mid-stream, changing the API
contract for any external C/ctypes caller. But `py_query_count()`
(`python_api.zig`) — the CPython-specific wrapper around `QueryCtx`'s
`Query.count()` — had zero remaining callers once Python's `count()`
moved fully onto the two parallel exports; removed it, its `_api.c`
glue (`api_count`, the `extern` declaration, the `"count"` method-table
entry), and `_open_query()`'s `_count_only` parameter (also confirmed
zero callers passing `True` — it existed solely to compute `max_column`
for the old count path). Full suite green after the removal.

## Relationship to csvql

csvql should eventually sit on top of libscanio (SQL parser/planner → libscanio → CSV/NDJSON) rather than duplicating scan logic. Extraction happens gradually, one primitive at a time, each step gated by csvql's existing correctness/fuzz/benchmark suite so it's provably zero-behavior-change before the next step starts. csvql remains the SQL product; libscanio is the reusable engine underneath it.
