# Roadmap

## Core principle

`scan()` is lazy and streaming by default. Never materialize the whole dataset unless explicitly asked (`.collect()` / equivalent).

## Milestones

- [x] **M1 — Scanner**: file source, CSV parser, `next()`, row streaming, constant-memory, Zig API. Originally mmap-based; switched to fixed-size chunked reads (`src/root.zig`) after measuring peak RSS against `cat` on a 417MB/1M-row/51-col file — mmap held 426MB resident (touching every byte to scan it faults in, and keeps resident, every page: peak RSS == file size by construction, regardless of the scanner logic on top), `cat` held 1.4MB (fixed-size read-and-discard loop). Chunked reads bring `Scanner` down into that same regime — bounded by chunk size, not file size, so a 10GB file costs the same working set as a 10MB one. Almost every row is still a zero-copy slice into the current chunk; only a line that straddles a chunk boundary gets assembled into a small reused scratch buffer instead. `count()`'s no-WHERE fast path was adapted to count newlines chunk-by-chunk (`Scanner.countRemaining()`) rather than over one large mapped slice — same zero-field-parse property, still bounded memory. NDJSON and JSON arrays got the same treatment shortly after — see M4's updated entry below.

  Chunk size swept, not guessed: 10 runs each, same 417MB/1M-row/51-col file.

  | chunk size | time avg | RSS avg |
  |---|---|---|
  | 64KB | 0.577s | 2.01MB |
  | **256KB (default)** | 0.563s | 2.20MB |
  | 1MB | 0.562s | 2.96MB |
  | 4MB | 0.565s | 6.13MB |
  | 16MB | 0.600s | 18.73MB |

  Time is flat (0.56-0.58s) from 64KB through 4MB — syscall count isn't the bottleneck anywhere in that range, even at 64KB (~6,500 `read()` calls for this file). RSS scales roughly linearly with chunk size, with no time payoff for going bigger. 16MB is a strict loss on both axes — the buffer itself gets big enough that first-touch cost starts to show. Landed on 256KB as the default: same time as 1MB, 26% less RSS, with enough margin over 64KB to avoid its slightly wider run-to-run variance. At the chosen default, versus the old mmap version: 427MB -> 2.2MB peak RSS, ~30% slower (0.43s -> 0.56s single-thread) — a real, named tradeoff made for the memory win, not hidden.

  Chunk size is configurable, not hardcoded: `Scanner.openWithOptions(allocator, path, .{ .chunk_size = N })` directly, or `Query.open(allocator, path, .{ .csv_chunk_size = N })` — `null` (the default either way) uses the measured 256KB default. Not exposed through the C ABI or Python binding yet (both use the default); add if a real caller needs to tune it, not speculatively.
- [x] **M2 — Scan operations**: projection, filter, limit, first, count. `count()` with no WHERE clause takes a zero-field-parse fast path (raw newline counting on the mapped bytes) — measured ~10x faster than a full row scan on a 500K-row file. `limit(N)` returns in time proportional to N, not file size (measured near-instant regardless of file size).
- [x] **M3 — C ABI**: `scanio_open` / `scanio_next` / `scanio_count` / `scanio_column_index` / `scanio_close` / `scanio_last_error`, minimal, no Zig internals exposed. Allocator is `std.heap.c_allocator`, not `GeneralPurposeAllocator` — this library gets `dlopen()`'d into a host process, and GPA's PageAllocator faults there (the exact bug csvql shipped once, #149). Verified for real: `zig build smoke-test` loads the built `.dylib`/`.so` via Python `ctypes` — the actual `dlopen()` path, not just Zig's in-process test runner — and runs 200 consecutive open/close cycles to catch allocator faults that only surface after repeated use.
- [x] **M4 — NDJSON, plus JSON arrays**: `src/ndjson.zig`, wired into `Query` via a `Source` tagged union so `scan("data.csv")` and `scan("data.ndjson")` (format inferred from extension, or explicit override) behave identically at every layer — filter, projection, limit, and the newline-only `count()` fast path all work the same for both, since both formats are one-record-per-line. `.json` files are also routed to the NDJSON path; the first non-whitespace byte (sniffed from the first chunk, see below) decides NDJSON-lines vs JSON-array. Nested objects/arrays *as field values* are still out of scope and fail loudly (`NestedValueNotSupported`) rather than silently stringifying.

  Originally mmap/full-load, same as CSV was before M1's fix, and for the same reason: measured 57.7MB peak RSS on a 56MB/1M-row NDJSON file and 51.1MB on an 11MB/200K-row JSON array file — both tracking file size, not row count. Rebuilt on the same chunked-read foundation as CSV (`NdjsonScanner` now has its own `buf`/`buf_len`/`buf_pos`/`line_scratch`, same shape as `Scanner`'s). NDJSON lines use the identical newline-boundary `nextLine()` CSV already has. JSON arrays needed a different boundary rule — no newlines to rely on inside `[{...},{...}]` — so `nextObject()` tracks brace depth and in-string/escape state across chunk refills instead, extracting one balanced `{...}` at a time; the old `json_array.zig::jsonArrayToNdjson()` (convert-the-whole-array-up-front) is no longer called by this path, kept only as a tested reference implementation. The header is derived from the first row's keys at `open()` time (same schema model as before) and that first row's text is cached and replayed as the first `next()` result, since a chunked reader can't rewind a file position the way a full mmap could.

  Measured, 10 runs each, old (mmap/full-load) vs new (chunked/streaming):

  | | time avg | RSS avg |
  |---|---|---|
  | NDJSON old, 56MB/1M rows | 0.176s | 57.72MB |
  | **NDJSON new** | 0.174s | **1.98MB** (29x less) |
  | JSON array old, 11MB/200K rows | 0.033s | 51.10MB |
  | **JSON array new** | 0.050s | **1.97MB** (26x less) |

  NDJSON's win is essentially free — same speed, 29x less memory, since line-splitting was never the bottleneck (JSON parsing dominates either way, unaffected by the I/O layer change — verified in isolation before trusting the headline number, since an earlier run of this same comparison showed a bogus 18x *slowdown* that turned out to be a stale, un-rebuilt benchmark binary, not a real regression). JSON array's win costs ~50% more time — the streaming brace-depth scan does genuinely more structural work per byte than one bulk convert pass followed by ordinary line-splitting did. Both are now bounded by chunk size regardless of file size, matching CSV and `cat`.

  Three real findings from actually measuring this, not assuming:

  1. The first implementation used `std.json.parseFromSlice` per line and measured 42K rows/sec vs CSV's 17M — 400x slower, building a full parse tree per row is real cost. Fixed by pulling in `json_parser.zig`/`json_simd.zig` from [zson](https://github.com/melihbirim/zson) (MIT, same author, vendored into `src/`) — a SIMD-tokenized, zero-copy JSON line parser already solving exactly this problem.
  2. Swapping the parser alone did *not* fix it — throughput was still ~39K rows/sec. The actual bottleneck was `std.heap.GeneralPurposeAllocator`'s per-allocation tracking overhead, not the parsing algorithm; switching the allocator passed to `Query.open()` to `std.heap.c_allocator` took it to 2.78M rows/sec — a 66x difference from allocator choice alone, on the identical parser and file. The C ABI already used `c_allocator` for an unrelated reason (GPA also faults when `dlopen()`'d), so Python callers got the fast path automatically the whole time — only the raw Zig-API benchmarks were measuring the slow path.
  3. Even with `c_allocator`, `NdjsonScanner` was still allocating and freeing a fields array (plus any escaped strings) fresh every row — a malloc/free pair per row, where CSV's `Scanner` does zero allocations per row via a reused, grow-not-reallocate `field_buf`. Replaced that with a `std.heap.ArenaAllocator` reset (`.retain_capacity`) at the start of each `next()` instead of individually freeing the previous row's `JsonObject` — reuses the same block across rows rather than returning it and re-requesting it every time, and skips `JsonObject.deinit()`'s per-field cleanup traversal entirely (arena reclaims everything in one reset). Took it to **4.3M rows/sec**.

  Final numbers, 500K rows: CSV 19.7M rows/sec / 12.8MB peak RSS, NDJSON 4.3M rows/sec / 25.4MB peak RSS — about 4.5x slower and 2x more memory than CSV. Not zero-copy parity (JSON structurally needs a per-row data structure CSV's flat field-split never does), but no longer 400x off, no longer unbounded, and now within the same order of magnitude as CSV rather than two orders away. Peak memory unchanged by the arena change — it retains the high-water-mark block rather than shrinking, a deliberate speed-over-footprint tradeoff, still bounded rather than growing.

  4. Done next: added `parseObjectReuse()` to `json_parser.zig` — same parsing logic as `parseObject()`, but the caller supplies a `fields` array to `clearRetainingCapacity()` and refill instead of a fresh `std.ArrayList` + `toOwnedSlice()` per call, same discipline CSV's `field_buf` already uses. `NdjsonScanner` holds that array as a persisted field, grown once via a real allocator and reused for the scanner's whole lifetime — not the per-row arena, which would defeat the reuse. One real bug this surfaced, caught by this file's own test suite (`ndjson: escaped strings decode correctly`): `owned_strings` (tracking escaped-string allocations) can't be persisted the same way, because `parseValueAfterColon()` grows *that* list using whatever single allocator it's handed — which for the reuse path is the per-row arena — so its backing array is arena-scoped, and freeing it later via the scanner's real allocator (a different allocator than whatever actually backed it) segfaulted. Fixed by keeping `owned_strings` local to each `next()` call instead of a persisted field.

  Effect depends on call pattern, reported honestly rather than picking whichever number looks best: in a **cold, single-process run** (the shape of a one-shot CLI/script invocation — `mem_check` scans once and exits), throughput went from 4.3M to 4.7M rows/sec — a modest ~10%, since first-touch costs (page faults, cold caches) dominate a short-lived process regardless of whether the code reuses buffers. In a **warm, repeated-call pattern within the same process** (5 runs back to back, first discarded), it went from an unmeasured baseline to a **steady ~6.0M rows/sec** — the reuse benefit compounds across calls once the working set is warm. CSV's own steady-state also jumps with warm-cache repetition (cold ~20M, warm ~44M on this hardware), so the CSV-to-NDJSON ratio lands around 4-7x depending on which regime you're comparing, not a single fixed number.

  Remaining lever, not yet done: the fields array is reused, but each row's *values* still get individually decoded/copied when escaped; a fully zero-copy path (only ever copying bytes that genuinely need unescaping, never touching the allocator for unescaped strings/numbers at all — which the parser mostly already does, per-field, but the per-row bookkeeping around it still costs something) is the next place to look if this needs to go further.
- [x] **M5a — Python binding**: `libscanio.scan(path, columns=[...], where="...", limit=...)` — the original target API. WHERE is a simple string (`col OP val [AND col OP val ...]`, no OR — the C ABI only represents a flat AND-list, and nothing has needed more than that yet). Column names are resolved to indices via one throwaway `scanio_open()` before the real, options-bearing open (the C ABI has no header-only entry point; two mmaps of the same file, not two reads, so the OS page cache absorbs it). Building this binding is also what surfaced a real C ABI gap — no way to list header column names — closed by adding `scanio_n_columns`/`scanio_column_name` to M3's surface rather than working around it in Python. Verified via `zig build python-test`, the real dlopen() path via ctypes, not just Zig's in-process tests; caught one real bug this way (two new C ABI functions missing from the ctypes `argtypes`/`restype` declarations caused a segfault — ctypes defaults to a 32-bit `c_int` return type, which mangles a 64-bit pointer/size_t).

  Later addition — `col IN (a, b, c)`: still no general OR (the C ABI's predicate list is still flat-AND-only), but IN covers the one case that gap actually blocked — "any of these values" — without needing N separate scans unioned in Python. New `Op.in_list` in `query.zig` (a predicate carries `values: []const []const u8` instead of one `value` when this op is used), a new `SCANIO_IN` C ABI op plus `values`/`n_values` fields on `scanio_predicate_t`, and `col IN (...)` syntax in the Python WHERE-string parser. One real ctypes gotcha worth naming: the `values` pointer in a `CPredicate` points at a ctypes array (`c_char_p * N`) that Python doesn't automatically keep alive just because a `CPredicate` references it — `_parse_where()` now returns that array alongside the predicates list (as `keepalive`) and every caller holds it in scope through the `scanio_open()` call that actually reads it, otherwise it risks being garbage-collected before or during the C call. Verified end to end on the real 417MB taxi fixture: `cab_type IN (yellow, green)` returned exactly 1,000,000 — matching the file's total row count, confirmed correct (not a bug) by checking yellow (967,553) + green (32,447) sums to exactly that.
- [ ] **M5b — Node binding**: not started.
- [ ] **M6 — Rust**: `cargo add libscanio`, C ABI first, idiomatic wrapper after.
- [x] **M7a — Aggregates + Top-K**: `aggregate()` computes count/sum/min/max/avg over a column in one streaming pass regardless of how many of those five you want — a second pass costs the same as the first. `topK()` adapts csvql's proven `TopKHeap` (`src/fast_sort.zig`, O(N log K) min/max-heap), minus its radix-sort key machinery (not needed for numeric-only top-K at this scope). Real cost named, not hidden: top-K has to retain K rows across the pass, and `Row.fields` point into a reused per-row buffer — so a candidate has to be copied to survive being kept. Mitigated, not eliminated: a row is only copied when `wouldAccept()` says it's an actual heap candidate, not for every row scanned. Measured on 500K rows: `topK(10)` costs about the same as a raw full scan (0.0191s vs 0.0283s) — one pass, not a full sort. Group-by not done (M7b, not started — no consumer has needed it yet).
- [x] **M8 — Higher-level adapter**: `mcp/` — an MCP server exposing scan/schema/profile/count/aggregate/topk as agent-callable tools. No MCP or AI-specific logic in libscanio itself — this is a separate consumer package (own `pyproject.toml`, own venv), a thin pass-through to the Python binding.

  Two of those six tools needed new C ABI surface first — `aggregate()` and `topK()` were Zig-only, never exposed past the C boundary. Added `scanio_aggregate()` (extern struct return: count/sum/min/max/avg + a `has_values` flag, since ctypes has no natural optional-float) and `scanio_topk()`/`scanio_topk_next()`/`scanio_topk_close()` (same open/next/close shape as the row scanner, walking a pre-sorted heap one entry at a time). Both drain the same `Ctx`/`Query` that `scanio_count()` already does — no new open path, no duplicated predicate-parsing. `Entry` (topk.zig's internal heap-slot type) had to become `pub` and get re-exported from `root.zig` for `c_api.zig` to name its type directly, instead of the type-inference hack that was there first (`@TypeOf(...).Item` on a value that doesn't have one — caught by `zig build test` failing to compile, not by review).

  `profile()` lives entirely in the Python binding, not the C ABI — it's schema() + count() + one aggregate() call per column that *looks* numeric (heuristic: does the first non-empty sampled value parse as a float). Real cost named, not hidden: each numeric column costs its own full scan, since `aggregate()` is one pass per call, not one pass total across columns — fine for an occasional profile call on an agent's first look at a file, not something to put in a hot loop over a wide file (the 51-column taxi fixture has 34 numeric-looking columns, so `profile()` on it costs roughly 34 full scans).

  Verified three ways, not just imported: `zig build test` (new C ABI tests: aggregate values, aggregate-with-no-numeric-values sets `has_values=0`, topk ordering, topk composing with a WHERE-filtered ctx), `zig build python-test` (26 tests now, up from 9 — schema/count/aggregate/topk/profile added, all through the real `dlopen()` path), and the MCP server's tools called through the actual `mcp` SDK's `call_tool()` path (not a direct Python call) against both a small fixture and the real 417MB/51-column taxi CSV — confirmed correct results including `profile()`'s 34-numeric-column classification and per-column real aggregates on that file.

  Follow-up, once real workload comparisons surfaced it: `libscanio.scan(...)` materialized into a Python list (`list(scan(...))`) was measured *slower* than a naive `csv.DictReader` loop doing the same filter in pure Python — 22.5s vs 10.8s on the 417MB/1M-row fixture, unprojected. Root cause: `scanio_next()` is one FFI call per row, and each row needs one `.decode()` per field — ~2M individual Python/C boundary crossings for a ~967K-row result, and that per-call cost dominates once you want every matching row back as real Python objects, not just a count. The Zig-side scan+filter itself is fast (0.43-0.48s, matches the pure-Zig `filter_bench` number) — the cost is entirely in how the result crosses into Python one field at a time.

  Fixed with a new C ABI path — `scanio_collect()`/`scanio_collect_data()`/`_n_rows()`/`_n_cols()`/`_close()` — that runs the WHOLE filtered scan in one C call and packs every matching row's fields into one NUL-separated buffer, handed to Python as a single `ctypes.string_at()` bulk copy instead of one call per field. `libscanio.scan_array()` wraps this: one bulk `decode()` over the whole buffer (not one per field — measured as the single biggest win, cutting the Python-side reshape from ~0.9s to ~0.06s on its own) and `zip(*[iter(parts)] * n_cols)` to chunk the flat field list into rows (~3x faster than index-slicing `parts[i*n_cols:(i+1)*n_cols]` per row, measured). End state on the same file/query/2-column-projection: `scan_array()` at ~0.61-0.69s steady-state, down from `list(scan())`'s 4.76-4.80s projected / 22.5s unprojected — a real ~7x win, not quite matching the pure-Zig 0.43-0.48s floor (materializing ~967K real Python tuple objects has its own irreducible CPython cost) but close.

  Real bug this surfaced along the way, not in the new code but in the benchmarking process itself: `zig build test` or `zig build python-test` run WITHOUT `-Doptimize=ReleaseFast` silently rebuilds `zig-out/lib/libscanio.*` at Debug as a side effect (it's a dependency of both steps), overwriting a prior ReleaseFast build at the same path with no error — cost real time twice in this session, chasing a "why is this suddenly 7x slower" regression that was actually a stale/wrong-optimization-level `.dylib`, not a real code regression. Documented directly in `build.zig` next to the `c-lib` step now: always rebuild `c-lib -Doptimize=ReleaseFast` as the LAST command before benchmarking anything against the shared library.

  `scan_array()` is deliberately NOT memory-bounded the way `scan()` is — it materializes every matching row in both Zig and Python at once, same tradeoff any "give me an array" API has. Use `scan()`'s generator and don't collect a list if the actual goal is staying within bounded memory on a file too big to hold in RAM; use `scan_array()` when you know the result set is manageable and want it back fast as real Python objects.
- [ ] **M9 — Parallel scan**: not started. Measured against `cat` on a 1M-row/51-col 417MB CSV, `Scanner` runs 0.42s single-thread (~2.4M rows/sec, CPU-bound on one core — `user` time tracks `real` time almost exactly). csvql does the same full-row scan in 0.16s on the same file, but only because it spreads the work across ~7-8 cores (`user` time is ~1.2s, well above `real`) — pinned to one thread (`--threads 1`), csvql takes 1.70s, ~4x *slower* than libscanio's single-thread `Scanner`. So the per-core scan loop is already solid; the gap is entirely the missing parallel path. A quick attempt to close it by switching `splitInto`'s scalar delimiter scan to `std.mem.indexOfScalarPos` (SIMD, mirroring how `nextLine()` finds `\n`) was tried and made things *slower* (0.42s -> 0.58s) — fields here average ~8 bytes, and indexOfScalarPos's per-call setup cost dominates below that length; reverted, see `splitInto`'s doc comment in `src/root.zig`. Getting from 0.42s toward csvql's 0.16s needs real parallel scanning (split the mmap into N chunks, one thread per chunk, align each chunk to a row boundary before scanning, merge/stream results) — a milestone, not a tuning pass. Deliberately not started yet: `Scanner`'s single-thread contract is simple and `dlopen()`-safe as-is; a threaded scan path changes that contract (thread pool lifecycle, cross-thread row ordering for a streaming `next()` API) and deserves its own design, not a bolt-on.

## V1 definition of done

```js
for await (const row of scan("50gb.csv", {
  columns: ["customer_id", "revenue"],
  where: "revenue > 1000",
  limit: 100
})) {
  process(row);
}
```

With: bounded memory, fast first-row latency, correct CSV parsing, Linux/macOS/Windows support, Zig API, C ABI, Node package, Python package. Everything else is secondary.

## Non-goals

Do not build: a database, a dataframe, a SQL parser, a query optimizer, distributed execution, an arbitrary-nested-JSON query engine, dataframe transformations, visualization, an AI agent, a GUI, or any mutation API (no update/delete/in-place edits/transactions — open, scan, close only).

## Benchmarking discipline

Correctness must be verified before any performance claim. Datasets: 10 MB / 100 MB / 1 GB / 10 GB. Scenarios: full scan, single-column projection, multi-column projection, filter at 50%/1% selectivity, `LIMIT 10`, `COUNT`, `SUM`, `TOP 10`. Measure rows/sec, MB/sec, memory, and time-to-first-row — not just throughput.

## Relationship to csvql

csvql should eventually sit on top of libscanio (SQL parser/planner → libscanio → CSV/NDJSON) rather than duplicating scan logic. Extraction happens gradually, one primitive at a time, each step gated by csvql's existing correctness/fuzz/benchmark suite so it's provably zero-behavior-change before the next step starts. csvql remains the SQL product; libscanio is the reusable engine underneath it.
